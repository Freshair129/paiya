# ป้ายยา (paiya) · แผนส่งมอบ

ให้ผู้ซื้อค้นประกาศหนึ่งรายการ เปิดหลักฐานที่ผูกกับประกาศนั้น และติดตามการเปลี่ยนสถานะได้บนข้อมูลจำลองก่อนเปิดตัวเก็บ Facebook ตารางนี้เป็นแผนสำหรับเปิด issue ตามลำดับการพึ่งพา บน main มีชุดตัวอย่างและตัวตรวจสัญญา v1 แล้ว การผ่านตัวตรวจเป็นหลักฐานด้านรูปแบบข้อมูล ส่วนงานรันระบบทั้งเส้นทางและการตรวจรับกับผู้ซื้อยังต้องดำเนินการ รหัสในตารางเป็นรหัสงานภายในแผน

ขอบเขตผู้ใช้อ้างอิง [PRD](../product/PRD.md) โครงสร้างระบบอ้างอิง [สเปกสถาปัตยกรรม](../architecture/SPEC.md) รูปแบบข้อมูลข้ามส่วนอ้างอิง [สัญญา Collector และ API](../architecture/contracts/collector-and-query.md) และเกณฑ์ตรวจรับเต็มอ้างอิง [SRS](../requirements/SRS.md)

## เส้นทางผู้ซื้อและการทดลองนำเข้าเอง (M)

พัฒนางาน M1–M4 บนข้อมูลสังเคราะห์ได้พร้อมระยะ A ลำดับแรกที่สาธิตได้คือ A1/A2 → M1 → M2 ตั้งแต่ต้นจนถึงกล่องแจ้งเตือน งานเปรียบเทียบและติดตามรายชิ้นเป็น P1 ตาม PRD ใช้ [ERD](../architecture/views/erd.md) และ [พจนานุกรมข้อมูล](../architecture/data-model.md) เป็นเกณฑ์ตรวจ migration และใช้ [กรณีทดสอบของผู้ซื้อ](../quality/buyer-acceptance.md) เป็นข้อมูลตั้งต้นร่วมกัน

| งาน | ผลส่งมอบและข้อที่รับผิดชอบ | ต้องมีก่อน | เงื่อนไขปิดงาน |
|---|---|---|---|
| M1 | ฟอร์มมือถือทวนข้อความก่อนบันทึก สิทธิ์นำเข้าและรอบสังเกต PR-10, FR-14 | A1/A2, ทบทวน ADR 0002, schema ใหม่และการแปลงจาก v1 | AT-11 พร้อมตรวจผู้เขียนตาม AT-03 ลิงก์นำเข้าไม่เกิดคำขอไปยัง Facebook คำขอซ้ำเป็นการบันทึกครั้งเดียว |
| M2 | ตั้งรับตามรุ่นและงบ กล่องแจ้งเตือนบนเครื่อง PR-11, FR-15 | M1 และการผูกสินค้า/ข้อเท็จจริงส่วนที่เกี่ยวข้องของ A4 | AT-12 ทดสอบสร้างกฎเมื่อมีข้อมูลเก่า ราคาข้ามงบ ข้อมูลไม่ครบ และ replay หลัง worker ขัดข้อง |
| M3 | ติดตามรายชิ้นและรวมงานตรวจที่ permalink PR-12, FR-16 | M1, Watch เดิมของ A4 และสิทธิ์ของแหล่ง | AT-13 ส่งข้อมูลของชิ้นข้างเคียงแล้วแจ้งเตือนของชิ้นที่เลือกเพิ่มศูนย์ ในโหมด M ไม่สร้างงานตรวจลิงก์ |
| M4 | เทียบ 2–3 ดีลและเปิดหลักฐานของแต่ละยอด PR-13, FR-17 | M1, ราคาหลายองค์ประกอบและการอ่านหลักฐาน | AT-14 ค่าส่งที่ไม่รู้ทำให้ยอดรวมยังไม่ทราบ ค่ามัดจำไม่นับเป็นราคาขาย ตรวจทุกชิ้นอีกครั้งเมื่อสิทธิ์เปลี่ยน |
| M5 | ทดลองกับผู้ซื้อและรายงานผล | M1–M4, การแสดงมือถือใน A5, การเพิกถอน/ลบ/กู้คืนที่เกี่ยวข้องใน A8 และผลทดสอบซ้ำบนเครื่อง | ผ่าน AT-03/05/08/09 และ AT-11 ถึง AT-14 ในขอบเขตนำเข้าเอง เก็บฐานเวลาแบบเดิมและติดตามเจ็ดวันตามแผน QA |

เจ้าของฐานข้อมูลเริ่ม migration จากตารางต้นทาง/สิทธิ์และคีย์โพสต์ ตามด้วยรอบสังเกต หลักฐาน สินค้า/ราคา แล้วจึงเพิ่มกฎและการแจ้งเตือน QA ทดสอบคู่ migration กับการ replay และ restore ก่อนใช้ข้อมูลผู้ซื้อ การทดลอง M ทำได้เมื่อผ่านเกณฑ์ของ M5 โดยไม่ต้องรอ B1 ส่วนการวัดความครอบคลุมของ Collector ต้องใช้ผล B2/B3

## ระยะ B · Collector อัตโนมัติตามคำตัดสินของเจ้าของ

เงื่อนไขเปิดใช้เป็นไปตาม [ADR 0005](../architecture/decisions/0005-owner-directed-collection.md) และตำแหน่งโค้ดตาม [ADR 0006](../architecture/decisions/0006-collector-monorepo.md): เจ้าของบันทึกคำตัดสินและขอบเขตต่อกลุ่มใน grant แทนหลักฐานสิทธิ์จากแพลตฟอร์ม โค้ด Collector อยู่ใน `collector/` แต่รันแยกจาก paiya และส่งผลผ่าน [inbox](../architecture/contracts/collector-inbox.md)

| งาน | ต้องมีก่อน | หลักฐานก่อนขยับขั้น |
|---|---|---|
| B1 บันทึกคำตัดสินของเจ้าของต่อกลุ่มและทดสอบการแยก session | A9 และทบทวนเกณฑ์ B แยกจาก M | มี grant ที่ระบุขอบเขต วัตถุประสงค์ และ retention ตาม ADR 0005 ทดสอบ credential จำลองกับลิงก์และ redirect สอง origin ให้ผลรั่วไหลศูนย์ บันทึกรุ่นของ adapter |
| B1a ความแม่นยำราคาของ AT-07 (A7b เดิม) | B1 และ parser ของ adapter ที่ผ่าน fixture | วัด amount, currency และรายการบนชุดที่คนติดป้ายอย่างน้อย 100 กรณีตาม SRS ข้อ 7 เฉลยผ่านการรีวิวของเจ้าของก่อนใช้ รายงานชุดย่อยราคาชัดเจน จำนวนตัวอย่าง และผลการแยกมัดจำ/ค่าขนส่ง ตรวจ AT-07 และ AT-10 |
| B2 ทดลองหนึ่งกลุ่ม | B1, B1a | เทียบโพสต์ที่ผู้ทดสอบเห็นในหน้าเดียวกันและรอบเดียวกัน ตรวจการผูกผู้ขาย สถานะรายชิ้น และรูป บันทึกจำนวนตัวอย่าง รอบที่ขาด และรอบที่เรียงล่าสุดไม่ได้ |
| B3 ขยายได้สูงสุดห้ากลุ่มที่เจ้าของบันทึก grant แล้ว | B2 ผ่านและแต่ละกลุ่มมี grant ครบ | วัดความล่าช้าของคิว CPU/RAM/VRAM และข้อผิดพลาดแยกตามกลุ่ม รายงานผล pilot แยกจาก fixture แล้วจึงตัดสินใจเปิดใช้ |

ถ้าพบการส่งข้อมูลล็อกอินข้าม origin หรือการยืนยันขายแล้วหรือผูกผิดผู้ขาย ให้ปิด live adapter ตาม SRS จนแก้สาเหตุและผ่าน regression test งานพัฒนาด้วย fixture เดินต่อได้

## ระยะ C · เปิดใช้งาน

ตัดสินใน [Issue #42](https://github.com/Freshair129/paiya/issues/42) รุ่นแรกที่เปิดใช้รันบน PC ของเจ้าของเครื่องเดียว API ผูก `127.0.0.1` ตาม [ADR 0004](../architecture/decisions/0004-local-access-and-mcp.md) การเปิดใช้ส่วนนำเข้าเองต้องผ่าน M5 ส่วน Collector อัตโนมัติต้องผ่าน B3 งาน O1–O4 พัฒนาและทดสอบด้วย fixture ได้ทันทีที่งานที่ต้องมีก่อน merge แล้ว โดยไม่ต้องรอระยะ B

| งาน | ผลส่งมอบ | ต้องมีก่อน | หลักฐานรับงาน |
|---|---|---|---|
| O1 สำรองและกู้คืน | งานสำรองรายวันและคำสั่ง restore ตาม [สเปกสถาปัตยกรรม](../architecture/SPEC.md) ข้อ 6 | A8 | restore ชุดสังเคราะห์ลงฐานและไดเรกทอรีสำรองได้ ตรวจ orphan และ hash ครบ รายการที่ลบไม่กลับมาค้นเจอ เปิด timeline และรูปผ่าน API ได้ |
| O2 สุขภาพระบบ | structured log ตาม SRS และหน้าจัดการที่แสดงคิวล่าช้า ช่องว่างการตรวจ อัตราภาพสำเร็จ พื้นที่ว่าง และเวลา backup สำเร็จล่าสุด | A3, A5, O1 | เทสต์จำลองดิสก์ใกล้เต็มแล้วระบบหยุดรับภาพใหม่และแจ้งเหตุ หน้าจัดการแสดงเวลา backup จริงเมื่อเครื่องปิดช่วงนัด |

## หลัง MVP

ประเมิน GenesisBlockDB เมื่อมีคำถามข้ามความสัมพันธ์ที่ต้องตอบ พร้อมเทียบผลกับ SQL และทดสอบ rebuild และ purge ส่วนการพยากรณ์ต้องกำหนดเป้าหมายและเกณฑ์ก่อนทำ backtest ตามเวลา เทียบกับการใช้ค่ามัธยฐานล่าสุด
