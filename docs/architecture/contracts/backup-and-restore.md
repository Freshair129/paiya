# สัญญาการสำรองและซ้อมกู้คืน (O1)

หน้านี้ขยาย [สเปกสถาปัตยกรรม](../SPEC.md) ย่อหน้า “สำรองและกู้คืน” ให้เป็นคำสั่ง รูปแบบชุดสำรอง และเกณฑ์ตรวจที่ทดสอบได้ ใช้คู่กับ [สัญญาการเพิกถอนและงานลบ](revocation-and-purge.md) ข้อ 4 (replay คำสั่งลบหลังกู้คืน), SRS ข้อ 6 และ AT-09 ตามแถว O1 ใน [ROADMAP](../../delivery/ROADMAP.md)

## 1. ขอบเขต

| ส่วน | เนื้อหา | ระดับความเสี่ยง |
|---|---|---|
| **O1a** | สร้างชุดสำรอง ตรวจชุดสำรอง กู้คืนลงฐานข้อมูลและไดเรกทอรีปลายทางใหม่ที่ว่างเท่านั้น บันทึกผลรอบสำรอง | กลาง (เพิ่มตาราง `backup_runs`) |
| **O1b** | ใช้การเข้ารหัสดิสก์ระดับ volume โดยเจ้าของเครื่อง ลบชุดเก่าด้วย `backup prune` และคงการกู้คืนทับระบบเป็นขั้นตอนมือใน runbook | สูง (การลบและการเขียนทับ) อนุมัติตามคำตัดสินเจ้าของใน [Issue #78](https://github.com/Freshair129/paiya/issues/78#issuecomment-6731424263) |

O1a ไม่ลบไฟล์หรือแถวใดในระบบต้นทาง และไม่เขียนลงฐานข้อมูลหรือไดเรกทอรีที่มีข้อมูลอยู่แล้ว

คำตัดสิน O1b ใช้ BitLocker หรือการเข้ารหัสดิสก์ระดับ volume แบบอื่นบนดิสก์สำรอง แอปไม่เก็บหรือจัดการกุญแจเข้ารหัส การลบของ `backup prune --apply` จำกัดอยู่ที่ชุดสำรองสมบูรณ์โดยตรงใต้ `PAIYA_BACKUP_DIR` เท่านั้น ไม่ลบฐานข้อมูลต้นทางหรือรายการอื่นในปลายทาง

## 2. ค่าตั้งและข้อจำกัดของปลายทาง

| ค่า | ความหมาย |
|---|---|
| `PAIYA_BACKUP_DIR` | ไดเรกทอรีปลายทางของชุดสำรอง กำหนดตอนติดตั้ง ไม่บันทึกในรีโป |
| `PAIYA_BACKUP_ALLOW_SAME_DEVICE` | `1` อนุญาตให้ปลายทางอยู่อุปกรณ์เดียวกับคลังภาพ ใช้ในเทสต์และการพัฒนาเท่านั้น ค่าเริ่มต้นปฏิเสธ |
| `PAIYA_PG_DUMP`, `PAIYA_PG_RESTORE` | คำสั่ง pg_dump/pg_restore ที่รองรับ PostgreSQL 17 ค่าเริ่มต้นคือชื่อคำสั่งใน PATH |

- ปลายทางต้องไม่อยู่ใต้คลังภาพ ใต้ไดเรกทอรีของ purge log หรือในรีโป และต้องอยู่คนละอุปกรณ์กับคลังภาพ (เทียบ `st_dev`) เว้นแต่ตั้ง `PAIYA_BACKUP_ALLOW_SAME_DEVICE=1` ซึ่งต้องปรากฏใน manifest เป็น `same_device_allowed: true`
- คลังภาพในระยะ A คือ `PAIYA_FIXTURE_MEDIA_ROOT`
- `backup prune` ตรวจข้อจำกัดปลายทางชุดเดียวกับ O1a ก่อนวางแผนทุกครั้ง และไม่สร้างไดเรกทอรีปลายทางที่ยังไม่มี

เมื่อฐานมีรอบ Facebook Collector คำสั่งสร้าง full backup จะปฏิเสธด้วย `collector_retention_unsupported` เพราะชุดสำรองปัจจุบันไม่มีการหมดอายุรายรอบตาม [สัญญา inbox](collector-inbox.md)

## 3. รูปแบบชุดสำรอง

หนึ่งชุดเป็นหนึ่งไดเรกทอรี `<PAIYA_BACKUP_DIR>/<YYYYMMDDTHHMMSSZ>-<backup_run_id>/` สร้างใต้ชื่อชั่วคราวแล้วเปลี่ยนชื่อแบบ atomic เมื่อครบ

| ไฟล์ | เนื้อหา |
|---|---|
| `db.dump` | `pg_dump --format=custom` ของ snapshot เดียวกับรายการภาพ |
| `media/<sha256[0:2]>/<sha256>` | สำเนาไฟล์ภาพตาม hash ทุกไฟล์ที่ตาราง media อ้างถึงใน snapshot |
| `manifest.json` | `format_version` (1), `backup_run_id`, `created_at`, `alembic_revision`, `app_version`, `db` (`file`, `sha256`, `bytes`), `media` (รายการ `sha256`, `bytes`), `settings` (เฉพาะค่าที่ไม่ใช่ secret ตามรายการอนุญาต), `same_device_allowed` |

- ห้ามมี secret ในชุดสำรอง เช่น รหัสผ่านใน `PAIYA_DATABASE_URL` คุกกี้ หรือกุญแจ `settings` ใช้รายการอนุญาตแบบระบุชื่อ ไม่ใช่การกรองชื่อออก
- ห้ามคัดลอก purge log (`PAIYA_PURGE_LOG_PATH`) ลงชุดสำรอง เพราะ [สัญญางานลบ](revocation-and-purge.md) ข้อ 4 ต้องเก็บบันทึกคำสั่งลบแยกจากชุดที่อาจกู้คืน
- `backup prune` พิจารณาเฉพาะไดเรกทอรีชุดสมบูรณ์ที่อยู่ตรงใต้ `PAIYA_BACKUP_DIR` ชื่อเป็น `<YYYYMMDDTHHMMSSZ>-<backup_run_id>` และ manifest ผ่านการตรวจ O1a เท่านั้น ไดเรกทอรีชั่วคราวที่ขึ้นต้นด้วยจุด รายการไม่รู้จัก symlink และ path ที่ resolve ออกนอกปลายทางจะไม่เป็น candidate

## 4. คำสั่ง

ทุกคำสั่งพิมพ์ผลเป็น JSON หนึ่งก้อน รหัสออก 0 เมื่อสำเร็จ และ 1 พร้อม `error.code` เมื่อไม่สำเร็จ ตามรูปแบบ CLI เดิม

1. **`paiya backup create`**
   - เปิดธุรกรรม `REPEATABLE READ` แล้ว export snapshot
   - อ่านรายการภาพจาก snapshot แล้วเรียก `pg_dump --snapshot=<id>`
   - คัดลอกไฟล์ภาพขณะถือ session advisory lock ตัวเดียวกับที่งานลบใช้ก่อนลบไฟล์ (A8b) งานลบไฟล์จึงรอจนคัดลอกเสร็จ ส่วน ingest เขียนต่อได้ เพราะไฟล์ภาพเป็นแบบ content-addressed และไม่ถูกเขียนทับ
   - ตรวจ SHA-256 ของทุกไฟล์ที่คัดลอกเทียบกับฐานข้อมูล ไฟล์ที่หายหรือ hash ไม่ตรงทำให้รอบนี้ `failed` ด้วย `error.code = media_missing` หรือ `media_hash_mismatch` และไม่เปลี่ยนชื่อชุดชั่วคราวเป็นชุดสมบูรณ์
   - การใช้ snapshot ร่วมกับ lock ของงานลบทำให้ได้จุดที่สอดคล้องกันตามเจตนา “หยุดการเขียนชั่วคราว” ใน SPEC โดยไม่ต้องหยุด API
2. **`paiya backup verify --set <dir>`**
   - อ่านชุดสำรองอย่างเดียว
   - ตรวจ manifest, hash ของ `db.dump` และทุกไฟล์ภาพ
   - รายงานไฟล์ที่เกินจาก manifest และไฟล์ที่หาย
3. **`paiya backup restore --set <dir> --target-database-url <url> --target-media-root <dir>`**
   - รัน `verify` ก่อน
   - ปฏิเสธเมื่อฐานปลายทางมีตารางใน schema `public` หรือไดเรกทอรีปลายทางมีไฟล์ (`error.code = target_not_empty`)
   - ปฏิเสธเมื่อปลายทางเป็นฐานหรือไดเรกทอรีเดียวกับระบบที่ใช้งาน
   - ลำดับงาน:
     1. `pg_restore` ลงฐานปลายทาง
     2. คัดลอกภาพตาม hash
     3. รัน `alembic upgrade head` เมื่อ revision ในชุดเก่ากว่า
     4. replay คำสั่งลบจาก purge log ปัจจุบันลงฐานปลายทางตาม [สัญญางานลบ](revocation-and-purge.md) ข้อ 4
     5. ตรวจ orphan สองทิศ (แถวที่ไม่มีไฟล์ และไฟล์ที่ไม่มีแถว)
     6. สุ่มเปิดโพสต์ไม่เกิน 5 รายการผ่าน API ใน process (timeline และรูปหนึ่งรูปต่อโพสต์ถ้ามี)
   - รายงานผลทุกขั้น ระบบปลายทางยังไม่เปิดให้ค้นจนกว่าทุกขั้นผ่าน (`ready: true`)
4. **`paiya backup status`**
   - คืนรอบสำรองสำเร็จล่าสุดจาก `backup_runs` พร้อม `completed_at` และ `age_hours`
   - คืนรอบล้มเหลวล่าสุดถ้ามี
   - O2 ใช้คำสั่งนี้แสดง “เวลาสำรองสำเร็จล่าสุดจริง”
5. **`paiya backup prune [--dry-run | --apply]`**
   - ค่าเริ่มต้นเทียบเท่า `--dry-run`; ไม่ลบหรือสร้างไฟล์
   - วางแผนจากชุดที่ manifest และ hash ผ่านการตรวจ คืน `keep[]`, `delete[]` และ totals โดยแต่ละรายการมีชื่อชุด `created_at`, เหตุผล และขนาดเป็น bytes ซึ่งรวม `st_size` ของไฟล์ปกติในชุด ชื่อเต็ม path จะไม่อยู่ในผลลัพธ์
   - เก็บชุดใหม่ที่สุดของแต่ละวัน UTC ใน 7 วันที่ล่าสุดซึ่งมีชุด และชุดใหม่ที่สุดของแต่ละ ISO week (ปี ISO และสัปดาห์) ใน 4 สัปดาห์ล่าสุดซึ่งมีชุด โดยเก็บผลรวมของสองหน้าต่าง
   - เก็บชุดใหม่ที่สุดโดยรวม ชุดล่าสุดที่ `backup_runs` ระบุว่า `succeeded` และชุดที่มีแถว `backup_runs` สถานะ `running` เสมอ
   - `--apply` วางแผนใหม่ทันที แล้วลบเฉพาะ candidate ในแผนใหม่นั้น fsync ไดเรกทอรีแม่เมื่อระบบรองรับ และรายงานผลรายชุด หากลบบางชุดไม่สำเร็จ คำสั่งคืนรหัสไม่เป็นศูนย์พร้อมชื่อชุดที่ยังเหลือและรหัสข้อผิดพลาดที่ไม่มี path

## 5. ตาราง `backup_runs`

- คอลัมน์: `id uuid`, `started_at`, `completed_at?`, `state` (`running`/`succeeded`/`failed`), `error_code?`, `db_bytes?`, `media_count?`, `media_bytes?`, `set_name?` (ชื่อไดเรกทอรีชุด ไม่ใช่ path เต็ม)
- เพิ่มด้วย migration ที่เพิ่มตารางอย่างเดียว downgrade ปฏิเสธเมื่อมีแถว ตามแบบ `0009_purge_jobs`
- O1b อ่านสถานะจากตารางนี้เท่านั้น ไม่เพิ่มหรือแก้ schema

## 6. เกณฑ์ตรวจ (fixture)

- **สำรองแล้วกู้คืน:** สำรองชุดสาธิตสังเคราะห์แล้วกู้คืนลงฐานและไดเรกทอรีชั่วคราวใหม่ จำนวนแถวของทุกตารางเท่าต้นทาง ทุกไฟล์ hash ตรง orphan เป็นศูนย์ เปิด timeline และรูปผ่าน API ได้ (ROADMAP O1)
- **ลบหลังสำรอง:** ลบขอบเขตหนึ่งหลังสำรอง แล้วกู้ชุดที่สำรองก่อนการลบ คำสั่งลบถูก replay ข้อมูลที่ลบค้นไม่เจอทั้ง API, MCP และสถิติ และไฟล์ภาพที่ไม่มี reference เหลือไม่ถูกคัดลอกกลับค้างไว้ (AT-09)
- **O1b retention:** สร้างชุดสังเคราะห์หลายชุดคร่อมขอบวัน UTC, ISO week และปี ISO รวมหลายชุดในวันเดียว ตรวจ dry-run ว่าไม่เปลี่ยนไฟล์ apply ว่าลบตรงกับแผนใหม่ และตรวจว่าชุดใหม่ที่สุด ชุดสำเร็จล่าสุด และชุดที่แถว `backup_runs` ยังเป็น `running` ไม่ถูกลบ
- **ขอบเขตการลบ:** ไดเรกทอรีชั่วคราว รายการไม่รู้จัก manifest เสีย symlink และ path ที่ resolve ออกนอก `PAIYA_BACKUP_DIR` ต้องไม่ถูกวางแผนหรือลบ ปลายทางที่ไม่ผ่าน O1a ต้องถูกปฏิเสธ ความล้มเหลวระหว่างลบต้องคืนรหัสไม่เป็นศูนย์และแสดงชื่อชุดที่ยังเหลือ โดยไม่มี full path ใน JSON
- **กรณีล้มเหลวมีเทสต์:**
  - ปลายทางไม่ว่าง
  - ปลายทางเป็นระบบที่ใช้งาน
  - ปลายทางสำรองอยู่ใต้คลังภาพ
  - อุปกรณ์เดียวกันโดยไม่ได้อนุญาต
  - ไฟล์ภาพหายหรือ hash ไม่ตรงระหว่างสำรอง
  - ชุดสำรองถูกแก้หลังสร้าง (verify ไม่ผ่าน)
  - ชุดที่สร้างไม่ครบไม่ถูกนับเป็นรอบสำเร็จ
- **ตรวจ secret:** ค้นทั้งชุดสำรองแล้วไม่พบรหัสผ่านของ URL ฐานข้อมูลหรือค่าใน `PAIYA_PURGE_LOG_PATH`
