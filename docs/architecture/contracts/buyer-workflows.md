# สัญญาการนำเข้าประกาศ ตั้งรับ ติดตาม และเทียบดีล

**สถานะ** แบบเสนอสำหรับพัฒนาและตรวจรับ · **ผู้ดูแล** Backend, PWA และ QA · **ผู้ใช้** ผู้ซื้อหนึ่งคนต่อการติดตั้ง

หน้าจอผู้ซื้อเรียก HTTP API บนเครื่องหลัก ฝั่งจัดเก็บใช้ PostgreSQL และภาพหลักฐานในเครื่อง เอกสารนี้กำหนดคำขอ ผลตอบกลับ และพฤติกรรมเมื่อข้อมูลขาด รุ่นของ HTTP ใช้ `/v1` ส่วน `schema_version` เป็นรุ่นของข้อมูล observation ที่ adapter ส่งเข้า backend ปัจจุบันมี schema และ fixture ที่ตรวจได้สำหรับ observation v1 เท่านั้น เส้นทาง HTTP กับ observation v2 ด้านล่างรอ implementation และการตรวจรับ [สัญญาเดิม](collector-and-query.md) · [แบบจำลองข้อมูล](../data-model.md) · [ข้อกำหนดระบบ](../../requirements/SRS.md)

## เส้นทาง API ที่เสนอ

| การกระทำ | คำขอ | ผลสำเร็จ |
|---|---|---|
| ดูตัวอย่างก่อนบันทึก | `POST /v1/imports/preview` ส่ง permalink ข้อความที่คัดลอก และภาพแนบถ้ามี | 200 พร้อม `preview_digest` รุ่นกฎ รายการ/ราคาที่แยกได้ ข้อความอ้างอิง และช่องที่ยังระบุไม่ได้ |
| ยืนยันนำเข้า | `POST /v1/imports` ส่งข้อมูลเดิมและ digest พร้อม header `Idempotency-Key` | 201 พร้อม `post_id`, `observation_id`, `item_ids`, `source_kind` และ `observed_at` การ retry ที่เคยบันทึกสำเร็จคืน 200 กับ ID เดิม |
| จัดการเงื่อนไขตั้งรับ | `POST /v1/buy-rules`, `GET /v1/buy-rules`, `PATCH /v1/buy-rules/{id}`, `DELETE /v1/buy-rules/{id}` | สร้าง 201 อ่าน/แก้ 200 ลบ 204 ผลการสร้างหรือแก้คืน ID รุ่นกฎ และภาวะพัก/เปิดใช้ |
| อ่านกล่องแจ้งเตือน | `GET /v1/alerts?cursor=…`, `PATCH /v1/alerts/{id}` กำหนด `read=true` | 200 พร้อมเหตุที่แจ้ง กฎหรือ watch ที่เกี่ยวข้อง post/item, observation, เวลาพบ และ evidence ID ที่ยังเปิดได้ การอ่านซ้ำคงสถานะเดิม |
| ติดตามชิ้นสินค้า | `PUT /v1/watches/{post_id}/items/{item_id}` และ `DELETE` ที่ URL เดียวกัน | 204 สั่งซ้ำได้ ตรวจว่าชิ้นนั้นอยู่ในโพสต์จริง การติดตามทั้งโพสต์ยังใช้ `/v1/watches/{post_id}` |
| เปิดหน้าเปรียบเทียบ | `GET /v1/compare?item_id=A&item_id=B` เพิ่ม `item_id=C` ได้ | 200 คืนรายการตามลำดับที่เลือก พร้อมเวลาของแต่ละค่า เหตุผลเมื่อขาดข้อมูล และทางเปิดหลักฐาน รายการที่เลือกมีอายุเท่าการเปิดหน้านี้ |

ทุกคำขอใช้ session ของแอป การเขียนตรวจ origin และ CSRF ทุกการอ่านตรวจ grant ของข้อมูลต้นทาง รวมถึงการอ่านแจ้งเตือนเก่าและการเปิดภาพ MCP ใช้ credential อ่านอย่างเดียวตามสิทธิ์เดิม ข้อความโพสต์และรูปอยู่ในขอบเขตข้อมูลภายนอกของระบบ [นโยบายการเข้าถึง](../SPEC.md)

## นำเข้าจากข้อความและหลักฐาน

**PR-10 · FR-14 · AT-11** ผู้ซื้อเลือกแหล่งที่มีสิทธิ์นำเข้าเอง วาง permalink กับข้อความ และเลือกแนบภาพเฉพาะส่วนได้ เมื่อกดดูตัวอย่าง API แยกรุ่น ราคา และช่วงข้อความบนเครื่อง ผู้ซื้อแก้การจับคู่ระหว่างชิ้นสินค้ากับข้อความที่เลือกแล้วดูตัวอย่างใหม่ได้ หลักฐานต้นฉบับเก็บตามขอบเขตสิทธิ์ ภาพเป็นไฟล์แนบให้คนอ่าน รุ่นนี้ใช้ข้อความที่ผู้ซื้อให้สำหรับการสกัด

ตัวอย่างการส่งข้อความสังเคราะห์ใน body ของ `POST /v1/imports/preview?group_id={group_id}` ผู้ทดสอบผูกกลุ่มจำลองใน URL เข้ากับ group ID ในเครื่องไว้ก่อน API ใช้ group ID ใน query เพื่อตรวจสิทธิ์ก่อนอ่าน body ทั้ง preview และ commit

```json
{
  "permalink": "https://www.facebook.com/groups/demo-group/posts/42/",
  "post_text": "RTX 3060 12GB 5,800 ค่าส่งใบนี้ 150"
}
```

ผล preview ยังไม่สร้าง observation เมื่อผู้ใช้กดยืนยัน ส่ง body นี้เพิ่มฟิลด์ `preview_digest` ที่ได้จาก preview ไปยัง `POST /v1/imports?group_id={group_id}` พร้อมคีย์การส่งที่สร้างครั้งเดียวต่อการยืนยัน บนมือถือให้เก็บคีย์นี้ไว้จนกว่าจะได้ผลสำเร็จหรือผู้ใช้เริ่มการส่งใหม่

1. **ระบุแหล่ง** ผูกแหล่งกับ grant สำหรับการนำเข้าเองตามวิธีรับข้อมูล ขอบเขตคอมเมนต์ ภาพ การอ่าน และอายุเก็บ ตรวจสิทธิ์ก่อนรับเนื้อหาและซ้ำก่อน commit เซิร์ฟเวอร์หา grant ด้วยกลุ่มและ `source_kind=manual_share` การนำเข้าทำงานด้วยการแยก URL ในเครื่องตลอดทั้ง preview และ commit ส่วน live collector ต้องมี grant ของวิธีเก็บนั้นเอง
2. **ระบุโพสต์** อ่าน group key และ stable post key จากรูปแบบ permalink ที่รองรับ ตัด query ติดตามที่ไม่ใช่ส่วนของตัวระบุ แล้วจับคู่กับกลุ่มที่เลือก ลิงก์แชร์สั้นที่ต้องตาม redirect, ลิงก์ต่างกลุ่ม หรือ URL ที่ระบุตัวโพสต์ไม่ได้ให้ขอ permalink ตรง โดยมีจำนวนคำขอเครือข่ายไปยังต้นทางเป็นศูนย์ ชื่อผู้ขาย ข้อความ ราคา หรือภาพซ้ำลำพังใช้รวมคนหรือโพสต์ข้ามกลุ่มไม่ได้
3. **ตรวจแล้วบันทึก** คำขอ preview และ commit รับข้อความและตัวเลือกเดิมเป็น JSON หรือ multipart เมื่อแนบภาพ digest ครอบคลุมแหล่ง permalink ข้อความ การจับคู่ชิ้นกับหลักฐาน hash ของภาพ และรุ่น parser ถ้า preview เก่าเกินใช้หรือเนื้อหาเปลี่ยน ให้ทำ preview ใหม่ ตรวจชนิด ขนาด และ hash จากไฟล์ที่รับจริง ใช้เวลาที่ server รับการยืนยันเป็น `observed_at` ส่วนเวลาที่ต้นทางแสดงให้เก็บตามความละเอียดที่ยืนยันได้
4. **แยก retry ออกจากการส่งรอบใหม่** ภายในขอบเขตผู้ซื้อ เก็บคีย์การส่งกับ digest และ ID ของผลที่ commit สำเร็จในธุรกรรมเดียวกัน การใช้คีย์เดิมพร้อมเนื้อหาเดิมคืนผลเดิมหลังตรวจสิทธิ์ปัจจุบัน คีย์เดิมที่ส่งเนื้อหาต่างกันได้ 409 การส่งโดยเจตนาอีกครั้งด้วยคีย์ใหม่เพิ่ม observation ใต้ post เดิม หากข้อเท็จจริงเหมือนเดิม เปลี่ยนเฉพาะเวลาที่รับข้อมูลและประวัติรอบ กฎธุรกิจไม่สร้างการเปลี่ยนสถานะหรือตั้งรับซ้ำ
5. **แสดงที่มา** ผลอ่านระบุ `source_kind=manual_share` กับเวลา “ผู้ใช้ส่งล่าสุด” เวลานี้ต่างจากวันลงประกาศ และต่างจากเวลาที่ collector ตรวจกลุ่ม งาน manual ไม่มีวันนัดตรวจหรือการเลื่อน checkpoint ข้อมูลที่ผู้ซื้อตัดมาเพียงบางส่วนมี coverage ตามส่วนที่ส่งมา

### การแมปไป observation v2

| ส่วนที่เปลี่ยน | ความหมายสำหรับ adapter และ backend |
|---|---|
| Envelope | สำหรับ manual ใช้ `source_kind=manual_share`, `job_kind=manual_import`, `page_check=null` และ `grant_id` ที่ระบุแหล่งตรงกันและมีสิทธิ์นำเข้า ส่วนงานผ่านเบราว์เซอร์ยังใช้ `discover` หรือ `revisit` พร้อมผลตรวจหน้าเว็บตามชนิดงาน |
| Post และ item | โพสต์มี stable key ภายในกลุ่ม หนึ่งโพสต์อาจมีหลายชิ้น แต่ละชิ้นที่จับคู่ข้ามรอบได้ต้องชี้หลักฐานระบุชิ้น การเพิ่มหรือสลับลำดับสินค้าในโพสต์ไม่ควรเปลี่ยน ID เดิม ถ้าสองชิ้นแยกไม่ออกให้คง `unresolved` จนกว่าจะมีหลักฐานพอ |
| ราคา | เสนอ `items[].price_facts[]` หลาย fact ต่อชิ้นและรอบ แต่ละ fact มี `kind`, `unit`, `currency`, `amount` แบบข้อความทศนิยม และคีย์หลักฐาน ราคาช่วงเก็บขอบเขตต่ำ/สูงเหมือน v1 ค่าส่งที่ยังผูกกับชิ้นไม่ได้คงเป็นข้อมูลระดับโพสต์จนกว่าจะมีหลักฐานระบุเงื่อนไข การย้าย v1 แปลงราคาเดิมหนึ่งค่าเป็นหนึ่ง fact และเก็บ `null` เป็นชุดว่าง |
| หลักฐาน | ตรวจ local key ของหลักฐานให้ไม่ซ้ำ ตรวจ post, item, observation และ grant เดียวกัน ตรวจ quote/offset กับข้อความต้นฉบับที่อ่านได้ บันทึกความไม่แน่นอนของบทบาทผู้พูด การที่ผู้ซื้อตรวจตัวเลขใน preview ไม่ได้พิสูจน์ว่าคนเขียนคอมเมนต์เป็นผู้ขาย |

ตัวอย่างส่วนของ item ที่ adapter v2 จะส่งหลังยืนยันราคาจากข้อความ “RTX 3060 12GB 5,800 ค่าส่งใบนี้ 150” ในรอบเดียวกัน โดย `e1` อ้างวลีราคาสินค้า และ `e2` อ้างวลีค่าส่งใน evidence ของ observation เดียวกัน

```json
{
  "source_item_key": "demo-3060",
  "model": "RTX 3060 12GB",
  "price_facts": [
    {"kind": "ask", "unit": "each", "currency": "THB", "amount": "5800.00", "evidence_key": "e1"},
    {"kind": "shipping", "unit": "each", "currency": "THB", "amount": "150.00", "evidence_key": "e2"}
  ]
}
```

**ก่อนรับ adapter v2** เพิ่ม JSON Schema และ fixture ชุดใหม่แยกไฟล์ ทดสอบอ่าน v1 และ v2 ฝั่ง backend ก่อนให้ adapter เริ่มส่ง v2 ต้องเล่น v1 เดิมซ้ำแล้วได้ post, item, ราคา และเหตุการณ์ชุดเดิม v1 ยังคงใช้ `items[].price` และ enum เดิม [Schema ที่มีจริง](observation.v1.schema.json)

**ก่อนสร้างสถานะจองหรือขายแล้ว** สำหรับคำยืนยันในคอมเมนต์ เบื้องต้นระบุ comment และ quote ให้ตรงกัน จากนั้นตรวจว่า role ของคอมเมนต์กับหลักฐานสอดคล้องกัน และมีหลักฐานยืนยันเจ้าของโพสต์ใน scope นั้น เช่น source actor key ตรงกัน เมื่อเห็นเพียงข้อความคัดลอกและยืนยันผู้พูดไม่ได้ ให้เก็บข้อความแต่คงสถานะเดิมหรือ unknown แยกกรณีป้ายสถานะจากต้นทางที่ตรวจที่มาได้ด้วย role `source_label` ทดสอบกรณีหลักฐานติด `seller` ชี้ข้อความ “จองครับ” ของ `other` ต้องไม่สร้างการจอง การขาย หรือการแจ้งว่าผู้ขายยืนยัน [SRS และ AT-03](../../requirements/SRS.md)

## ตั้งรับและติดตามชิ้นสินค้า

**PR-11 · FR-15 · AT-12** กำหนดกฎกับชิ้นสินค้า เช่น รุ่นตรง `RTX 3060` หน่วยความจำ 12 GB สกุล THB เพดานราคาตั้งขายต่อชิ้น 6,000 บาท สภาพและข้อยกเว้นที่ผู้ซื้อเลือก ฟิลด์บังคับที่ยังไม่ทราบให้ผล “ข้อมูลไม่พอ” รุ่น Ti, VRAM 8 GB หรือหลักฐานระบุชัดว่าขายเฉพาะยกชุดให้ผลว่าไม่ตรงเกณฑ์ ตัวเลขมัดจำ ค่างวด และยอดเสนอซื้อเก็บตามชนิดของตัวเอง ถ้าเห็นเพียงยอดเหล่านี้แล้วไม่มีราคาตั้งขายที่ใช้ได้ ให้ผล “ข้อมูลไม่พอ” พร้อมคงผลที่เคยยืนยัน จึงไม่แจ้งซ้ำเมื่อกลับมาเห็นราคาตั้งขายเดิม สำหรับเพดานราคาตั้งขายที่เป็นตัวเลขเดี่ยว ค่าเท่ากับเพดานถือว่าผ่าน ค่าส่งที่ยังไม่ทราบไม่เปลี่ยนราคาตั้งขายที่ใช้ประเมิน หากมีเพียงช่วงราคาที่คร่อมเพดาน ผลยังไม่ชัดเจน

| ประวัติของกฎและชิ้น | เมื่อประเมินข้อมูลที่มีสิทธิ์รอบนี้ | ผลในกล่องแจ้งเตือน |
|---|---|---|
| สร้างกฎ แก้เงื่อนไข หรือเปิดกฎที่เคยพัก | ตั้งค่าตั้งต้นจากของที่มี ณ จุดเริ่มใช้รุ่นกฎ ผู้ซื้อเปิดดูรายการที่เข้าเงื่อนไขอยู่แล้วได้ | ไม่ส่งแจ้งย้อนหลัง |
| ชิ้นใหม่หลังเริ่มกฎ หรือเดิมยังไม่เคยตรงและไม่มีข้อสรุป | พบหลักฐานครั้งแรกว่าตรงครบ | เพิ่มหนึ่งรายการพร้อมเหตุที่ตรงและ observation |
| เคยตรง | รอบใหม่ยังตรง อ่านไม่ได้ หรือมีฟิลด์ที่จำเป็นขาด | ไม่แจ้งซ้ำ รอบที่ขาดหลักฐานไม่ล้างผลที่เคยยืนยัน |
| เคยตรง จากนั้นมีหลักฐานยืนยันว่าออกนอกเงื่อนไข | มีรอบใหม่ยืนยันว่ากลับเข้าเกณฑ์ | แจ้งการกลับเข้าเกณฑ์หนึ่งครั้ง |
| Replay หรืองานเก่ามาถึงหลังหลักฐานใหม่กว่า | เพิ่มหลักฐานย้อนหลังได้ตามสิทธิ์ | ไม่ย้อนสถานะล่าสุดและไม่เปิดเหตุแจ้งซ้ำ |

เก็บกฎใน `buy_rules` ผลล่าสุดกับผลที่ยืนยันได้ครั้งก่อนใน `rule_item_states` ตาม `(rule_id, rule_revision, item_id)` และข้อความใน `alerts` ตาม `cause_key` ของเหตุที่ทำให้ชิ้นนั้นเข้าเกณฑ์ จัดลำดับประเมินตาม observation ที่มีผลจริง ตรวจ idempotency ของเหตุเปลี่ยนและบันทึกสถานะกับข้อความแจ้งในธุรกรรมเดียว การสร้าง baseline ต้องมีจุดแบ่งรอบชัดเจน เพื่อให้ observation ระหว่างสร้างกฎถูกประเมินครั้งเดียวหลัง baseline การเพิกถอน grant ซ่อนรายการนั้นจากผลแมตช์ กล่องแจ้ง และรายละเอียดทันที งาน purge ล้างข้อมูลอนุพันธ์ที่เกี่ยวข้องตาม SRS การประเมินในโหมด manual เกิดเมื่อผู้ใช้นำข้อมูลเข้ามา รุ่นแรกแสดงการแจ้งเตือนภายในแอป

**PR-12 · FR-16 · AT-13** `watches.item_id` ที่มีค่าจำกัดเหตุแจ้งราคาหรือสถานะให้เหลือเฉพาะชิ้นนั้น ค่า null แทนการติดตามทั้งโพสต์ ถ้าผู้ซื้อเฝ้าทั้ง 3060 และ 3070 ในโพสต์เดียว แหล่ง live ที่มีสิทธิ์ใช้การตรวจ permalink รอบเดียวร่วมกัน ขณะที่ของที่ผู้ใช้นำเข้าเองจะประเมินใหม่เมื่อส่งข้อมูลครั้งถัดไป การซื้อขายของชิ้นที่ระบุไม่ได้ให้ขึ้น “ต้องตรวจสอบ” บนโพสต์ โดยงดแจ้งการเปลี่ยนสถานะรายชิ้นจนระบุเป้าหมายได้

## เปรียบเทียบดีล

**PR-13 · FR-17 · AT-14** รับ 2–3 item ID ที่ต่างกันและอ่านได้ทั้งหมด ส่งคืนรุ่น ผู้ประกาศเท่าที่ยืนยันได้ สถานะขายรายชิ้นพร้อมเวลาและหลักฐาน สภาพ ประกันตามถ้อยคำผู้ขาย ราคาตั้งขายต่อชิ้น เงื่อนไขส่ง ยอดที่คำนวณได้ เวลาสังเกต และ evidence ID แยกต่อค่า ถ้ารายการต่างหน่วย สกุล หรือรุ่นย่อย ให้แสดงความต่างก่อนเปรียบราคาและงดจัดอันดับยอดที่เทียบไม่ได้

| ข้อความที่มีหลักฐาน | ราคาตั้งขาย | ค่าส่ง | ยอดรวมที่แสดง |
|---|---:|---|---|
| “5,800 บาท ส่ง 150 สำหรับใบนี้” | 5,800 | 150 บาท | 5,950 บาท |
| “5,900 รวมส่ง” | 5,900 | รวมในราคา | 5,900 บาท |
| “5,900” | 5,900 | ยังไม่ทราบ | null พร้อมป้าย “ยังไม่ทราบยอดรวม” |
| “มัดจำ 500” | ยังไม่ทราบ | ยังไม่ทราบ | null เงินมัดจำแสดงตามประเภท |
| “ขายคู่ 11,000 ส่ง 100 ทั้งกล่อง” | 11,000 ต่อชุด | 100 ต่อชุด | ยังไม่ทราบยอดต่อชิ้น |

การคำนวณยอดสำหรับจัดส่งต้องมีราคาตั้งขายชิ้นเดียวที่ชัดเจนและเงื่อนไขส่งที่ตรงกับชิ้นนั้น ราคาต้นทางที่รวมส่งแล้วนับครั้งเดียว ยอดผ่อน มัดจำ คำเสนอซื้อ และค่าส่งคลุมเครือไม่ใช้เติมส่วนที่ขาด เมื่อข้อมูลเก่าหรือเข้าถึงไม่ได้ ให้แสดงเวลาของหลักฐานและภาวะอ่านได้ล่าสุดตามต้นทาง หากสิทธิ์ถูกเพิกถอนระหว่างดู ให้ปิดการอ่านทั้งข้อมูลและภาพในคำขอถัดไป

## ตัวอย่างสำหรับตรวจรับเส้นทางเดียวตั้งแต่นำเข้าถึงผู้ซื้อ

ข้อมูลทุกชิ้นในตารางเป็นข้อมูลสังเคราะห์ ผู้ซื้อเปิดกฎ “RTX 3060 12GB ≤ 6,000 บาทต่อชิ้น” ก่อนนำเข้า โพสต์ A ขาย 3060 กับ 3070 ส่วนโพสต์ B ขาย 3060 อีกใบ

| ลำดับ | ข้อมูลเข้า | ผลที่ต้องตรวจ |
|---|---|---|
| 1 | ส่ง A “3060 12GB 6,300 / 3070 8GB 7,900” | ได้หนึ่งโพสต์ สอง item และหนึ่ง observation กล่องตั้งรับยังว่าง ผู้ซื้อเลือกติดตามเฉพาะ 3060 |
| 2 | ส่ง A รอบใหม่ “3060 12GB ลดเหลือ 5,800 ค่าส่งใบนี้ 150” | 3060 ID เดิม ราคา/ค่าส่งชี้ข้อความต้นทาง กฎตั้งรับมีหนึ่งเหตุเข้าเกณฑ์ ชิ้น 3070 คงหลักฐานเดิม |
| 3 | retry คำขอข้อ 2 ด้วยคีย์เดิม แล้วส่งข้อความเดิมโดยตั้งใจอีกครั้งด้วยคีย์ใหม่ | retry คืน ID เดิม การส่งใหม่เพิ่ม observation หนึ่งรอบ จำนวนเหตุเข้าเกณฑ์ยังเท่าเดิม |
| 4 | ใน fixture มี source actor key ของผู้โพสต์ตรงกับผู้เขียน “3070 ขายแล้ว” อีกคอมเมนต์ของผู้ซื้อระบุว่า “จอง 3060 ครับ” ทดลองอีกครั้งด้วยการส่งเฉพาะข้อความคัดลอกใน M | ใน fixture เปลี่ยนเฉพาะสถานะของ 3070 การติดตาม 3060 ไม่มีเหตุยืนยันจองหรือขาย ใน M ที่ยืนยันผู้พูดไม่ได้ให้เก็บข้อความไว้ โดยคงสถานะเดิมหรือ unknown หากยังไม่มีหลักฐานสถานะ |
| 5 | ส่ง B “3060 12GB 5,900” แล้วเปิดเปรียบเทียบ 3060 จาก A กับ B | ผล A แสดง 5,950 บาท ผล B แสดงราคาตั้งขาย 5,900 บาทและยอดรวมยังไม่ทราบ กลับมาตรวจข้อความอ้างอิงของทั้งคู่ได้ |

## ข้อผิดพลาดที่ client ต้องรองรับ

| ตอบกลับ | การกระทำของ client |
|---|---|
| 401 ยังไม่ยืนยันตัว, 403 session ไม่มีสิทธิ์ใช้คำสั่งเขียน | กลับหน้าเข้าสู่ระบบหรือแสดงว่าใช้คำสั่งนี้ไม่ได้ |
| 404 ID ไม่มีอยู่หรืออยู่นอกขอบเขตการอ่าน | ใช้ข้อความเดียวกันทุกกรณี การเปรียบเทียบที่มีชิ้นนอก scope แม้เพียงชิ้นเดียวคืน 404 ทั้งคำขอโดยไม่ส่งรายการที่เหลือ ผู้ซื้อยังเปิดชิ้นที่มีสิทธิ์ในคำขอใหม่ได้ |
| 409 คีย์การส่งเดิมกับเนื้อหาใหม่ หรือ digest ตัวอย่างไม่ตรง | หากข้อมูลเปลี่ยน ให้ตรวจตัวอย่างใหม่และใช้คีย์การยืนยันใหม่ |
| 413 ไฟล์ใหญ่เกินกำหนด, 415 ชนิดไฟล์ไม่รองรับ | ให้ลดขนาดหรือเปลี่ยนไฟล์แล้วลองใหม่ |
| 422 ลิงก์ระบุตัวโพสต์ไม่ได้ ชิ้นไม่อยู่ในโพสต์ที่อ่านได้ หรือจำนวน/ID ที่เลือกเทียบผิด | คืนชื่อฟิลด์และสาเหตุให้แก้โดยคงข้อความร่างของผู้ซื้อไว้ |

คำตอบข้อผิดพลาดประกอบด้วย `code` ที่คงที่และ `field` เมื่อระบุได้ คำขออ่านข้อมูลและภาพใช้ `private, no-store` ทดสอบผลร่วมกับการเพิกถอน การลบ และการ restore ก่อนเปิดให้ใช้งานจริง [เกณฑ์รับมอบ](../../quality/TRACEABILITY.md)
