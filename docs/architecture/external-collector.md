# สเปก Collector ภายนอกของป้ายยา

**สถานะ** แบบสำหรับพัฒนาและทดสอบด้วยข้อมูลสังเคราะห์ · 10 พฤศจิกายน 2026 · อ้างอิง paiya `102c36a`

**ผู้ดูแล** เจ้าของโปรแกรม Collector ดูแลการอ่านต้นทางและไฟล์ส่งออก เจ้าของ paiya ดูแลสัญญา inbox และการรับข้อมูล

Collector ทำงานบน Windows เครื่องเดียวกับ paiya ผู้ใช้เลือกกลุ่มและรอบตรวจ โปรแกรมอ่านประกาศที่โหลดให้เห็น เก็บข้อความกับภาพที่ใช้เป็นหลักฐาน แล้วส่งผลหนึ่งชุดต่อรอบทางโฟลเดอร์ในเครื่อง ผู้พัฒนาทดลองได้ตั้งแต่อ่าน HTML สังเคราะห์จนถึงตรวจชุดส่งออกผ่าน CLI โดยไม่ต้องเปิดบัญชี Facebook

## 1. ขอบเขตงานและส่วนประกอบ

| ส่วน | รับผิดชอบ |
|---|---|
| การตั้งค่าและตารางงาน | เจ้าของกำหนดกลุ่ม, group key, grant ID, ขอบเขตข้อมูล, วันหมดอายุ, retention และรอบตรวจ เก็บข้อมูลกำกับงานและประวัติการส่งในเครื่องของ Collector |
| Browser adapter | เปิดหน้าที่กำหนด ตรวจตัวตนกลุ่ม สถานะ session และลำดับฟีด อ่านการ์ดระหว่างเลื่อนก่อนที่ DOM จะถูกแทนที่ แยกการอ่านหน้าออกจากกฎแปลงการ์ด เพื่อให้ parser ทดสอบกับ fixture ได้ |
| ตัวแยกประกาศและหลักฐาน | สร้าง observation v1 แยกโพสต์ สินค้ารายชิ้น ผู้พูด และหลักฐาน เก็บเท่าที่ grant ครอบคลุม |
| ตัวเขียน inbox | ตรวจความสัมพันธ์ของ ID สร้างไฟล์ผลรอบและไฟล์ภาพ แล้วเผยแพร่ไดเรกทอรีที่เขียนเสร็จด้วยการ rename ครั้งเดียว |
| paiya | I1 เปิดไฟล์ที่ระบุและรายงานผลตรวจแบบออฟไลน์ ส่วน I2 ซึ่งจะตรวจ grant กับฐานข้อมูลและนำเข้าข้อมูลจริงอยู่ใน [Issue #91](https://github.com/Freshair129/paiya/issues/91) |

โค้ด producer อยู่ใน subproject [`collector/`](../../collector/) ของรีโปเดียวกับ paiya ตาม [ADR 0006](decisions/0006-collector-monorepo.md) แต่ติดตั้งและรันเป็น process แยก ใช้ Python 3.12, Chromium โปรไฟล์เฉพาะงาน และ parser ที่ทดสอบด้วยไฟล์สังเคราะห์ โปรแกรมไม่เชื่อม PostgreSQL หรือ MCP; จะใช้ Ollama ในเครื่องได้ตามที่ผู้ใช้เปิดเอง การตัดสินสถานะขาย การรวมประวัติผู้ขาย และการคำนวณแนวโน้มราคาอยู่ฝั่ง paiya โค้ดใน [src/paiya/collector](../../src/paiya/collector) ยังคงเป็น worker สำหรับ fixture ภายในแอป ส่วน Collector ภายนอกส่งผลผ่าน inbox เท่านั้น

## 2. สิ่งที่เจ้าของควบคุมได้

- เปิด พัก หรือยกเลิกการติดตามได้สูงสุด 5 กลุ่ม ตั้งรอบค้นโพสต์ใหม่แยกกลุ่มที่ 30 หรือ 60 นาที ถ้าใช้หน้าต่างแบบมองเห็นได้ อาจคงหนึ่งแท็บต่อกลุ่มเพื่อให้ตรวจด้วยตา แต่คิวอ่านหรือ refresh ทีละหนึ่งงานทั้งเครื่อง
- ตรวจกลุ่มและขอบเขตก่อนเปิดหน้าและก่อนส่งชุดข้อมูล หากข้อมูลกำกับ grant หาย หมดอายุ ถูกพัก หรือยืนยันสถานะที่เจ้าของกำหนดไม่ได้ ให้หยุดงานกลุ่มนั้น ข้อมูลกำกับฝั่ง Collector เป็นการตั้งค่าของโปรแกรมภายนอก การตรวจไฟล์ I1 ไม่ยืนยันว่า grant ในฐานข้อมูลยังใช้ได้
- แสดงเวลานัด เวลาตรวจจริง รอบที่เผยแพร่ล่าสุด เวลาเริ่มตรวจได้อีกครั้ง และเหตุที่พักเป็นรายกลุ่ม เวลาในไฟล์เป็น UTC ลงท้าย `Z` หน้าโปรแกรมแสดงเวลาไทยได้ เมื่อเครื่องหลับให้รวม slot ที่ค้างเป็นหนึ่งรอบปัจจุบันและจดช่วงที่พลาดไว้ในเครื่อง
- โหมดติดตาม permalink แยกจากการค้นบนฟีด เป้าหมายตามสเปกคือเร่งตรวจทุก 10 นาที ครั้งละ 24 ชั่วโมง รวมสูงสุด 10 โพสต์ และใช้งบร่วมต่อกลุ่ม เมื่อคิวแน่นให้ discovery ได้ทำก่อน ระยะส่งมอบแรกเปิดเฉพาะ discovery ผ่าน inbox ส่วน revisit มีเงื่อนไขความเข้ากันได้ในข้อ 5 [สัญญาคิว](contracts/discovery-queue.md) · [สัญญา Watch](contracts/item-status-and-watches.md)

## 3. รอบค้นประกาศใหม่

1. สร้าง `run_id` สำหรับงานของกลุ่มและ slot นั้น บันทึก ID ก่อนเริ่มอ่านเพื่อให้กู้จากการปิดโปรแกรมกลางรอบได้ ตรวจว่าหน้าเป็นกลุ่มที่เลือก ตรวจสถานะ session แล้วเลือกโพสต์ใหม่ ตรวจข้อความหรือสถานะการเลือกที่ UI แสดงจริง ถ้าผิดกลุ่มให้หยุด ห้ามผูกการ์ดกับกลุ่มที่ตั้งใจเปิด
2. อ่านการ์ดที่โหลดแล้วตามลำดับ บันทึก `cards_seen`, `cards_parsed` และ `scroll_steps` แยกกัน เริ่มด้วยงบต่อรอบ 120 วินาทีหรือ 30 ขั้นการเลื่อน หยุดเมื่อถึงเพดานใดก่อน การ์ดที่ขาด stable post key ให้นับเป็นการแยกล้มเหลว
3. หา overlap จากการ์ดธรรมดาที่มีคีย์อยู่ก่อนเริ่มรอบ 3 ใบติดกัน โพสต์ปักหมุดและโพสต์แนะนำข้ามได้โดยไม่เพิ่มหรือรีเซ็ตจำนวน ทำสำเนาชุดคีย์ประจำกลุ่มก่อนเริ่มรอบจากคีย์ที่แยกได้และเผยแพร่สำเร็จในรอบก่อน รวมรอบ partial ด้วย ชุดนี้แยกจาก top 20 ใน checkpoint การ์ดที่เพิ่งเห็นซ้ำครั้งแรกภายในรอบไม่นับเข้า overlap และตัวโปรแกรมไม่ต้องอ่านตารางของ paiya
4. สรุป coverage ตามตาราง ก่อนเผยแพร่ให้ตรวจความสัมพันธ์ของ run, grant, group, จำนวนการ์ดที่เห็น และ envelope ที่สร้างได้ เก็บ checkpoint ท้องถิ่นได้สูงสุด 20 คีย์แรกของการ์ดปกติ เลื่อนต่อเมื่อรอบ `complete` เผยแพร่สำเร็จเท่านั้น ผลตรวจรูปแบบผ่านเป็นคนละเหตุการณ์กับการนำเข้า SQL สำเร็จ

| สิ่งที่พบ | ผลรอบและผลต่อ checkpoint |
|---|---|
| ยืนยันการเรียงได้ ถึง overlap โดยไม่มีเหตุ partial หรือรอบแรกอ่านจบฟีดในงบและมีการ์ดที่อ่านได้ | `complete` เฉพาะขอบเขตรอบที่สังเกตได้ |
| ยืนยันการเรียงไม่ได้, หมดงบก่อน overlap, ฟีดจบก่อน overlap ทั้งที่เคยมีโพสต์ หรือมีการ์ดแยกคีย์ไม่ได้และยังอ่านบางการ์ดได้ | `partial` ระบุทุกเหตุที่เข้าเงื่อนไข ส่งรายการที่ใช้ได้ คง checkpoint เดิม |
| เข้าไม่ได้หรือไม่มีการ์ดที่อ่านได้ | `none` พร้อมเหตุที่ตรงสัญญา คง checkpoint เดิม รอบที่ไม่มี envelope ยังมี run summary |
| เหตุการณ์เกิดและหายระหว่างสองรอบ | เก็บเฉพาะที่สังเกตได้ ใช้เวลาตรวจจริง ไม่สร้างเวลาเริ่มจอง ยกเลิก หรือปิดขายย้อนหลังจากการคาดเดา |

## 4. สิ่งที่เก็บจากหนึ่งโพสต์

| ข้อมูล | กฎของ parser |
|---|---|
| โพสต์และผู้ขาย | อ่าน stable post key, permalink และผู้ลงประกาศภายในขอบเขตการ์ดเดียวกัน ถ้าเห็นเพียงชื่อ ให้เก็บตัวระบุผู้ขายเป็น null ตาม schema และแยกคนชื่อเดียวกันไว้ เวลาอย่าง “5 ชม.” คงข้อความต้นทางและความละเอียดตามที่ทราบ |
| รายการสินค้าและราคา | หนึ่งโพสต์มีหลายชิ้นได้ รักษาคีย์สินค้าเมื่อยืนยันชิ้นเดิมได้ แยก ask, มัดจำ, ค่าส่ง, ค่างวดและราคาเหมา รวมสกุลเงินกับหน่วย ถ้าผูกจำนวนเงินกับชิ้นใดไม่ได้ ให้ใช้ค่าไม่ทราบตามสัญญา |
| คอมเมนต์และสถานะ | แยกยอดที่ต้นทางแสดง จำนวนข้อความที่อ่านได้ และจำนวนบัญชีที่แยกได้ “จองครับ” จากผู้ซื้อเป็นคำพูดของ `other` ส่วนคำยืนยันขายของเจ้าของโพสต์ต้องผูกกับชิ้นและข้อความจริง กรณีผู้เขียนไม่ชัดใช้ `unknown` รักษาป้ายจากหน้าเว็บตามที่เห็น |
| ข้อความและภาพหลักฐาน | ส่งข้อความอ้างอิงใน `source_span` ตาม v1 และอ้างคอมเมนต์ของรอบเดียวกันเมื่อใช้ความเห็นเป็นหลักฐาน ครอปเฉพาะสินค้าหรือข้อความจำเป็น ใช้ WebP/JPEG ที่ยังอ่านใจความสำคัญได้ บันทึก MIME, SHA-256, bytes และขนาดของไฟล์ปลายทาง หากไม่ร้องขอภาพ ต้นทางไม่มีภาพ หรือเก็บไม่ได้ ให้ใช้ `media_state` ที่ตรงเหตุ |
| ข้อมูลที่เก็บนอก bundle | โปรไฟล์ล็อกอินอยู่เฉพาะเบราว์เซอร์ ห้ามส่ง cookies, token, credential, รหัสบัญชีของผู้ใช้ Collector เอง หรือ HTML ดิบลงไฟล์ รวมถึงข้อความ log ที่แนบกับผล ห้ามติดตามลิงก์ภายนอกที่ฝังในโพสต์ |

ใช้ [observation v1](contracts/observation.v1.schema.json) และ [ความหมายฟิลด์กับกฎข้ามฟิลด์](contracts/collector-and-query.md) เป็นหลัก ตัวอย่าง `post_text` ของ manual share v2 เป็นสัญญาอีกช่องทางหนึ่ง

## 5. กรณีที่ต้องหยุดหรือพักการส่ง

| เหตุการณ์ | การตอบสนองที่ต้องทำ |
|---|---|
| Login, checkpoint, challenge หรือสิทธิ์ถูกปฏิเสธ | หยุดการเข้าหน้านั้นทันที ใช้ session/coverage/error ตามสัญญา พักงานที่ใช้ session เดียวกันเมื่อปัญหาอยู่ที่บัญชี ให้เจ้าของกลับมายืนยันก่อนทำต่อ ไม่ลองบัญชีอื่นอัตโนมัติ |
| HTTP 429 | เคารพ `Retry-After` เก็บเวลารอไว้ในเครื่องข้าม restart ถ้าไม่มีค่าที่ใช้ได้ให้พักและรอเจ้าของหรือใช้นโยบาย backoff ที่กำหนดไว้ก่อนทดลอง คง checkpoint ปัจจุบัน สัญญา I1 ยังไม่มี error code เฉพาะสำหรับ 429 ให้เก็บเหตุนี้ในบันทึกงานท้องถิ่นและพักการส่งรอบที่ยังแทนความจริงไม่ได้จนตกลง mapping |
| โพสต์เดิมซ้ำในรอบเดียว | เนื้อหาเดิมใช้ capture เดิม ส่งหนึ่งไฟล์ต่อคีย์ หากเนื้อหาเปลี่ยนให้รักษาข้อมูลขัดกันเป็นข้อผิดพลาดของรอบในเครื่อง ห้ามเขียนทับ envelope หรือสร้าง capture ID ใหม่เพื่อหลบ conflict งดเผยแพร่รอบกำกวมและคง checkpoint จนมีคำตัดสินว่าจะเก็บครั้งแรก ครั้งสุดท้าย หรือหยุดรอบตาม [Issue #76](https://github.com/Freshair129/paiya/issues/76) |
| ตรวจ permalink โดยตรง | v1 กำหนด `page_check.sort=not_applicable` สำหรับ revisit และ fixture worker ใช้ `stop_reason=null` เมื่อสำเร็จ แต่ I1 รับ `run.sort_result` เพียง `verified_latest/unverified` และรับ stop reason เฉพาะชุด discovery ห้ามใส่ค่าเรียงล่าสุดหรือ `feed_end` สมมติ ใช้ fixture ทดสอบได้ เปิดส่ง revisit ภายหลังเมื่อทั้ง producer และ I1 ผ่านตัวอย่างเดียวกัน |
| ดิสก์เต็ม เขียนรูปไม่ได้ หรือ process ถูกปิด | งานที่ยังไม่ atomic rename ไม่ปรากฏเป็นรอบพร้อมรับ ถ้าเสียเฉพาะภาพให้บันทึก `capture_failed` ตามสัญญา ถ้าเขียน summary หรือหลักฐานข้อความไม่ได้ให้คง checkpoint และพักงานจนพื้นที่พร้อม |

ก่อนทดลองกับกลุ่มจริง เจ้าของบันทึกกลุ่ม วัตถุประสงค์ ขอบเขตและ retention ตาม ADR 0005 ทดสอบด้วย credential จำลองกับสอง origin ทั้งลิงก์และ redirect ให้พบการส่ง credential ข้ามขอบเขตศูนย์ครั้ง ห้ามใช้ stealth, fingerprint spoofing หรือวิธีหลบการตรวจจับ การตัดสินใจรายกลุ่มเป็นของเจ้าของและไม่ใช่คำรับรองจากแพลตฟอร์ม

## 6. ส่งมอบหนึ่งรอบผ่าน local inbox

- ตั้ง inbox นอกรีโป นอกคลังภาพ และนอก purge log ผู้เขียนใช้เฉพาะ `incoming/` ส่ง `source_kind=facebook_live` และ `payload.schema_version=1` แม้ใช้ข้อมูลสังเคราะห์เพื่อทดสอบสัญญานี้ ทุก envelope ต้องมี group, run, grant และ job ตรงกับ summary กำหนด `capture_id = uuid5(UUID(run_id), source_post_key)`
- เขียน `incoming/.<run_id>.tmp/run.json`, `envelopes/<capture_id>.json` และภาพใน `assets/` ให้ครบ สร้างโฟลเดอร์ `envelopes/` และ `assets/` แม้ว่าง เขียนไฟล์ว่าง `READY` เป็นลำดับสุดท้าย ปิดไฟล์ทั้งหมด แล้วเปลี่ยนชื่อบน volume เดียวกันเป็น `incoming/<run_id>/` โดยไม่ทับปลายทาง
- หลัง restart หากพบ UUID ที่เผยแพร่แล้ว ให้เทียบกับบันทึกการส่งก่อนทำงานต่อ เมื่อยืนยันไม่ได้ให้พักเพื่อทวนสอบ รอบที่เผยแพร่แล้วต้องไม่ถูกแก้หรือส่งซ้ำด้วย UUID ใหม่ บันทึกเฉพาะ run ID, เวลา จำนวน และเหตุที่ต้องแก้ ห้าม producer ย้ายไฟล์ไป `processing/`, `done/` หรือ `rejected/`
- บังคับ retention กับข้อมูลที่ producer เป็นเจ้าของด้วย ทั้งคีย์ที่ใช้เทียบรอบ ไฟล์ชั่วคราว ภาพค้าง และสำเนาสำหรับตรวจ เมื่อเพิกถอนให้หยุดส่งและล้างสำเนาเหล่านี้ตามขอบเขต เหลือเพียงผลดำเนินการที่ไม่มีเนื้อหา ข้อมูลที่ส่งถึง paiya แล้วใช้กระบวนการเพิกถอนและลบฝั่งผู้รับ [สัญญาการเพิกถอน](contracts/revocation-and-purge.md)
- ตรวจด้วย CLI ในไดเรกทอรีที่ชื่อฐานตรง UUID จริง ใช้ปลายทางหลัง rename หรือสำเนาแยกที่มีชื่อถูกต้อง เมื่อมี consumer I2 ให้ตรวจสำเนาชื่อ UUID ในพื้นที่ส่วนตัวก่อนส่งจริง เพื่อไม่แข่งกับการย้ายไฟล์ของผู้รับ การรันกับ `.<run_id>.tmp` จะถูกปฏิเสธแม้เนื้อหาไฟล์ถูกต้อง รูปแบบไฟล์และตัวอย่างเต็มอยู่ใน [สัญญา inbox](contracts/collector-inbox.md) และ [ตัวอย่างหนึ่งรอบ](../../fixtures/inbox/valid-complete/11111111-2222-4333-8444-555555555555/run.json)

## 7. เกณฑ์รับงานฝั่งผู้เขียน Collector

จับคู่การตั้งกลุ่มกับ FR-01, การเรียงและความครอบคลุมกับ FR-02/03, หลักฐานกับ FR-05/07 และ grant กับ FR-13 ใช้ผลของ AT-02, AT-04, AT-05, AT-07 และ AT-09 เฉพาะส่วนที่ทดสอบจริง [SRS](../requirements/SRS.md) · [ตารางตรวจย้อนกลับ](../quality/TRACEABILITY.md)

| กรณีทดสอบสังเคราะห์ | หลักฐานผ่านที่ต้องส่งกับ PR ของ Collector |
|---|---|
| Discovery อ่านฟีดเรียงล่าสุด ปักหมุด โพสต์ซ้ำ ฟีดขาด และ DOM นำการ์ดออก | เทียบรายการคีย์ที่คนติดป้ายว่าโหลดเห็นได้ต่อรอบ รายงานตัวเศษและตัวหาร AT-02 ≥95% ค่า coverage และการเลื่อน checkpoint ต้องตรงคำตอบทุกเคส |
| แยกคำพูด ราคาและหลักฐาน | ผู้ซื้อจองอย่างเดียวไม่ถูกระบุเป็นคำยืนยันของผู้ขาย ผู้ขายชื่อซ้ำไม่ถูกรวมผิด ภาพทุกชิ้นเปิดกับโพสต์เดียวกับข้อความ ทดสอบราคา B1a อย่างน้อย 100 เคสที่คนติดป้าย รายงาน AT-07 ≥95% สำหรับจำนวนเงิน สกุลเงินและชิ้นของชุดย่อยราคาเสนอขายชัดเจน |
| Login/challenge, 429, รอบขาด, grant ไม่พร้อม | เห็นการพักและเวลาที่จะตรวจใหม่หลัง restart คง checkpoint รอบล่าสุด กรณี challenge ไม่มีการเปิดหน้าเพิ่ม รอบ `none` ที่แทนได้ส่ง bundle ว่างถูกต้อง |
| เขียนและส่งใหม่ | จำลอง crash ก่อนและหลัง rename ผู้อ่านเห็นศูนย์หรือหนึ่งชุดที่สมบูรณ์ เปลี่ยน hash, MIME หรือ path แล้ว validator ต้องคืน exit 1 รายงานสาเหตุโดยไม่แสดง secret |
| การแยก session และข้อมูล | ทดสอบ redirect ข้าม origin ด้วยค่า canary; ไม่พบค่านั้นที่ปลายทางหรือใน bundle/log ทดสอบด้วย HTML สังเคราะห์ที่ไม่มีเครือข่ายและไฟล์ภาพที่เผยแพร่ได้ |

**คำสั่งตัวอย่างจากรากรีโป paiya** หลัง `uv sync --locked` ให้รันชุดรับเข้าที่มีอยู่ก่อน แล้วใช้คำสั่ง validate เดิมกับไดเรกทอรีที่ Collector สร้างเอง

```sh
uv run python -m paiya.cli inbox validate fixtures/inbox/valid-complete/11111111-2222-4333-8444-555555555555
uv run pytest -q tests/test_i1_inbox_validate.py
```

ตัวอย่างแรกต้องได้ exit 0, `ok=true`, `envelopes_checked=1` และ `problems=[]` การผ่าน fixture ของ paiya ยืนยันความเข้ากันได้ของตัวอย่างที่มากับรีโป ทีม Collector ต้องส่งผลจาก **bundle ที่ parser ของตัวเองสร้าง** พร้อมเวอร์ชัน adapter, commit, fixture และผลเคสล้มเหลวก่อนรับงาน เมื่อ B1 และ B1a ผ่าน จึงพิจารณา B2 หนึ่งกลุ่ม แล้ว B3 สูงสุดห้ากลุ่มตาม [Roadmap](../delivery/ROADMAP.md) สิทธิ์เปิด ingest ข้อมูลจริงเป็นคำตัดสินแยกใน Issue #91


### ผลตรวจความเข้ากันได้ ณ ฐานอ้างอิง

ที่ `102c36a` ตรวจ [ชุดทดสอบ I1](../../tests/test_i1_inbox_validate.py) ผ่าน 30 กรณี และทดลองส่งสำเนา fixture ในไดเรกทอรีชั่วคราวด้วย CLI ได้ผลดังนี้

| รอบสังเคราะห์ | ผลจาก validator |
|---|---|
| Discovery ที่มี envelope หนึ่งไฟล์ / รอบไม่มีข้อมูลที่มีโฟลเดอร์ว่างครบ | exit 0 ทั้งคู่ ตรวจได้ 1 / 0 envelope ตามลำดับ |
| Revisit ที่สำเร็จ ใช้ sort `not_applicable` และ stop reason เป็น null | exit 1, `run_enum` ที่ `run.json#/sort_result` และ `run.json#/stop_reason` |
| รอบไม่มีข้อมูลที่ส่ง `error_code=rate_limited` | exit 1, `run_enum` ที่ `run.json#/error_code` |

ผลนี้ใช้ตัดสินว่างานใดเริ่มทดสอบออฟไลน์ได้ การรันกับเบราว์เซอร์และกลุ่มจริงยังไม่มีผลรับรองในสเปกฉบับนี้
