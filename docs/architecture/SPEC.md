# ป้ายยา (paiya) · ข้อกำหนดสถาปัตยกรรม

**รุ่น 0.2 | 7 พฤศจิกายน 2026 | สถานะ ข้อเสนอสำหรับสร้างและทดสอบ MVP**

ผู้ซื้อใช้ป้ายยาบน PC เครื่องเดียวเพื่อเก็บประกาศฮาร์ดแวร์มือสอง ตั้งรับตามรุ่นและงบ และย้อนดูที่มาของข้อมูล เส้นทางนำเข้าเองรับข้อความจากผู้ใช้ ส่วนตัวเก็บแบบตั้งรอบเปิดได้เฉพาะแหล่งที่ได้รับสิทธิ์ ผู้ใช้เปิดดูรูป ราคา ผู้ขาย และหลักฐานจากรอบล่าสุดที่ระบบตรวจได้ สเปกนี้กำหนดขอบเขตของบริการและการส่งข้อมูล ส่วนเงื่อนไขผลิตภัณฑ์อยู่ใน PRD พฤติกรรมและเกณฑ์ตรวจรับอยู่ใน [SRS](../requirements/SRS.md) ส่วนข้อมูลข้ามบริการอยู่ใน [สัญญา Collector และ API](contracts/collector-and-query.md)

## 1. Stack ที่ใช้

| ส่วน | เทคโนโลยีและตำแหน่งรัน | ความรับผิดชอบ |
|---|---|---|
| แอปผู้ใช้ | React + TypeScript + Vite, PWA | ดูสินค้า บันทึกรายการติดตาม ดูผู้ขายและเวลาหลักฐาน ออกแบบที่ความกว้างมือถือก่อน ขยายเป็นมุมมองรายการและรายละเอียดบนเดสก์ท็อป |
| HTTP API | Python 3.12, FastAPI, Pydantic บน Windows | เสิร์ฟไฟล์แอปที่ build แล้ว, JSON API และรูปจาก origin เดียว ตรวจสิทธิ์ก่อนอ่านหลักฐาน ตรวจ schema ทุกครั้งที่รับข้อมูล |
| งานเบื้องหลัง | Python worker หนึ่ง process บน Windows | วางรอบงาน ดึงโพสต์ ตรวจลิงก์เดิม นำเข้า fixture และประมวลผลข้อมูล งานแยกประเภทอยู่ในคิว SQL เดียว จัดลำดับให้การค้นโพสต์ใหม่ได้ทำตามรอบ |
| ตัวเก็บข้อมูล | Scrapling 0.5.1 สำหรับ PoC, Chromium ใช้โปรไฟล์แยกบน Windows | เขียนตัวอ่าน Facebook เฉพาะทาง ให้ประเมินผลด้วย fixture ก่อนเปิดใช้งานจริง แยกการอัปเดตไลบรารีจากการเปลี่ยนกฎจำแนกสถานะ |
| ฐานข้อมูล | PostgreSQL 17 ใน Docker Compose ผ่าน WSL2, SQLAlchemy + Alembic | แหล่งข้อมูลหลักสำหรับกลุ่ม โพสต์ รายการสินค้า ราคา สถานะ ความสัมพันธ์ ผู้ขาย คิวงานและข้อมูลกำกับหลักฐาน |
| ที่เก็บภาพ | ไดเรกทอรีบน volume ถาวรของ Windows ที่เข้ารหัส | เก็บภาพลดขนาดหรือภาพครอปสินค้า ผูกกับ observation ผ่าน evidence ID และ SHA-256 รองรับสำรองและตรวจความสมบูรณ์ |
| AI ในเครื่อง | Ollama บน Windows ผ่าน loopback, โมเดลภาษาไทยหนึ่งตัวและ inference ทีละงาน | ช่วยสกัดรุ่น สภาพ ราคาและแท็กจากข้อความกำกวม ผลลัพธ์เป็น JSON ตาม schema ระบุข้อความหรือหลักฐานต้นทาง |
| ทางเข้าสำหรับ Agent | MCP ผ่าน stdio บนเครื่อง | Adapter แบบอ่านอย่างเดียวเรียก API เดียวกับแอป ใช้ค้นประกาศ ประวัติผู้ขายและเรียกภาพตามสิทธิ์ |
| การวิเคราะห์ | SQL สำหรับ MVP, GenesisBlockDB เป็นส่วนขยายระยะถัดไป | SQL สรุปการเคลื่อนไหวของราคาประกาศย้อนหลัง ส่วนกราฟรับการเปลี่ยนแปลงหลัง commit เมื่อมีกรณีใช้งานที่ต้องเดินกราฟจริง |

ติดตั้ง API, worker, Chromium และ Ollama ในสภาพแวดล้อม Windows เดียวกัน การแสดงเบราว์เซอร์หรือการให้ผู้ใช้ยืนยัน session จึงทำบนเครื่องที่มีโปรไฟล์โดยตรง ให้ Docker เปิดพอร์ต Postgres เฉพาะ loopback และ mount ข้อมูล DB บน volume ถาวรภายใน WSL2 ใช้ Vite เป็น build tool และ dev server เฉพาะตอนพัฒนา เมื่อใช้งานจริง FastAPI ให้บริการแอปโดยตรง ตัวระบบจึงเริ่มได้ด้วยฐานข้อมูลหนึ่งชุดและแอป Python สอง process

## 2. เส้นทางข้อมูล

ดูจุดที่ Worker บันทึกข้อมูล เรียก AI และส่งหลักฐานให้หน้าแอปหรือ Agent ได้จาก [ภาพเส้นทางข้อมูลจากรอบตรวจถึงผู้ซื้อ](views/observation-flow.md)

**เส้นทางจากมือถือ** PWA ส่งลิงก์และข้อความให้ FastAPI แสดงส่วนที่สกัดได้พร้อมข้อความอ้างอิง ผู้ใช้ยืนยันก่อนเขียนลงคลัง API ตรวจสิทธิ์นำเข้าในเครื่องและคีย์กันส่งซ้ำ ลิงก์ใช้ระบุโพสต์และเปิดเมื่อผู้ใช้เลือกไปต้นทาง การวางลิงก์หรือเปิดดูตัวอย่างต้องสร้างคำขอไปยังต้นทางเป็นศูนย์ ภาพแนบเป็นหลักฐานเสริม ระยะ M ใช้ข้อความเป็นข้อมูลตั้งต้น

**จากข้อเท็จจริงไปถึงดีล** Worker ตรวจผู้เขียน บทบาท และชิ้นสินค้าก่อนเปลี่ยนสถานะ อ่านราคาเสนอขายและค่าส่งเป็นคนละข้อเท็จจริงพร้อมหลักฐาน เมื่อข้อมูลรายชิ้นเปลี่ยนจึงประเมินกฎของผู้ซื้อและบันทึกการแจ้งเตือนในแอปพร้อมคีย์กันซ้ำ หน้าเปรียบเทียบอ่านข้อมูล ณ เวลาขอและตรวจสิทธิ์ของแต่ละชิ้น [ERD](views/erd.md) · [แบบจำลองข้อมูลและคีย์](data-model.md) · [สัญญาฝั่งผู้ซื้อ](contracts/buyer-workflows.md)

**ขอบเขตการนำเข้า** ตัวอ่านแต่ละแหล่งส่ง JSON รูปแบบกลางพร้อมรุ่น schema, run ID, ตัวตนแหล่ง/โพสต์, เวลาที่เห็น, ขอบเขตคอมเมนต์และการอ้างถึงภาพ หลักฐานของการนำเข้าทดสอบระบุ provenance แยกจากข้อมูลจริงและใช้ namespace แยก เพื่อไม่ให้ตัวอย่างไปปนประวัติผู้ขายหรือค่ากลางราคา สร้าง Markdown จากข้อมูลที่ผ่านการตรวจเมื่อต้องส่งออกหรือให้คนอ่าน

**ขอบเขตการตัดสินสถานะ** บันทึกสิ่งที่เห็นก่อนจัดหมวดหมู่ เก็บราคาเป็นจำนวนเงินและสกุลเงินที่ระบุได้ แยกราคาขายต่อชิ้น ราคายกชุด ค่ามัดจำและค่าส่ง โพสต์หนึ่งมีได้หลายสินค้า ความเป็นเจ้าของประกาศต้องยืนยันได้จากภายในโพสต์เดียวกัน ก่อนนำคำพูดของผู้ขายมาเปลี่ยนสถานะของสินค้าที่เกี่ยวข้อง เช่น ผู้ซื้อเขียน “จองครับ” เก็บเป็นกิจกรรมสนใจ ผู้ขายระบุ “3060 ติดจอง เหลือ 3070” อัปเดตเฉพาะรายการ 3060 และอ้างถึงข้อความนั้น สัญญาณขัดกันที่แก้ด้วยลำดับเวลาและแหล่งที่มาไม่ได้ต้องขึ้นรอตรวจ

**ขอบเขตการตอบคำถาม** API คืนทั้งค่าและเวลาที่ตรวจได้ เช่น หากมีตัวเลข 5 ที่หัวคอมเมนต์ ระบบตอบว่าแหล่งข้อมูลแสดง 5 คอมเมนต์ การตอบว่า “มีคนมา 5 คน” ต้องมีผู้แสดงความเห็นที่แยกตัวตนได้ห้ารายจริง แสดงเวลาโพสต์ เวลาพบครั้งแรก และเวลาตรวจล่าสุดแยกกัน ทั้งแอปและ Agent อ่านจากชุดข้อมูลสิทธิ์เดียวกัน

## 3. การค้นโพสต์ใหม่ และการกลับไปดูโพสต์เดิม

ตารางงานในหัวข้อนี้ใช้กับการจำลอง Collector ระยะ A และแหล่งที่ได้รับสิทธิ์เก็บอัตโนมัติระยะ B เท่านั้น การนำเข้าเองระยะ M จะได้ข้อมูลรอบใหม่เมื่อผู้ใช้ส่งอีกครั้ง

1. **ตั้งค่ากลุ่ม** รองรับห้ากลุ่มช่วงเริ่มต้น ผู้ใช้กำหนดรอบ 30 หรือ 60 นาทีรายกลุ่ม หยุด/เปิดแต่ละกลุ่มได้ มีสถานะสิทธิ์ ขอบเขตที่อนุญาตและวันหมดอายุ ให้หนึ่งกลุ่มเป็นหนึ่งตารางงาน Browser Worker ใช้โปรไฟล์เฉพาะและเปิดทีละงาน
2. **ยืนยันการเรียงล่าสุด** หลังเข้าแต่ละกลุ่ม ตรวจตัวระบุกลุ่มและสถานะที่ UI เลือก “โพสต์ใหม่” จริงแล้วจึงเก็บผลเป็นรอบเรียงล่าสุด แยกโพสต์ปักหมุดและโพสต์ที่แนะนำ หากยืนยันตัวเลือกไม่ได้ บันทึกรอบที่การเรียงไม่แน่นอนและรักษาจุดอ้างอิงเดิม
3. **อ่านแบบมีขอบเขต** เก็บการ์ดระหว่างเลื่อนเพราะฟีดอาจเปลี่ยน DOM ตลอดเวลา ใช้ช่วงซ้อนกับโพสต์รอบก่อนและตรวจโพสต์ทั่วไปหลายรายการที่ต่อเนื่องกัน บันทึกเกณฑ์หยุดและจำนวนที่ตรวจได้ หากถึงเพดานเวลาก่อนถึงช่วงซ้อน ให้ส่งสิ่งที่อ่านสำเร็จและระบุว่ารอบนี้ได้เพียงบางส่วน รอบแรกจดขอบเขตเริ่มต้นไว้ให้ตรวจย้อนหลังได้
4. **ติดตามรายการสำคัญ** เมื่อผู้ใช้เลือกติดตาม ให้ตั้งงานตรวจ permalink โดยตรงทุก 10 นาทีภายในงบของแหล่ง งานนี้แยกจากการเปิดฟีด และทำได้เมื่อขอบเขตสิทธิ์ครอบคลุม แบ่งงบให้การค้นโพสต์ใหม่ก่อน เมื่อคิวแน่นแสดงเวลาตรวจจริงและรอบถัดไปตามคิว ใช้ post ID เดิมทุกครั้งและบันทึก observation ใหม่ตามรอบ
   รายการใหม่ที่ยังไม่มีหลักฐานว่าปิดขายให้เข้าคิวตรวจปกติตามรอบกลุ่มใน 24 ชั่วโมงแรก เรียงจากรายการที่ค้างนานที่สุดภายในงบของกลุ่ม ถ้าเวลาไม่พอให้แสดงว่าเลยกำหนด การติดดาวคงอยู่จนผู้ใช้ยกเลิก ส่วนการเร่งรอบ 10 นาทีเป็นสิทธิ์เพิ่มเติมที่หมดอายุได้
5. **ความครอบคลุม** บันทึกเวลานัด เวลาลงมือ เวลาตรวจสำเร็จ จำนวนการ์ดที่เห็น/แยกได้ เหตุที่อ่านได้เพียงบางส่วน ตลอดจนวันเวลาและเหตุผลของช่วงที่ขาด เครื่องหลับหรือ offline ให้รวมงานค้างเป็นหนึ่งรอบติดตามต่อและเก็บช่วงขาดไว้ การเห็นข้อมูลเดิมก่อนและหลังช่วงขาดยังเปิดโอกาสให้มีการเปลี่ยนแปลงแล้วลบระหว่างนั้น
6. **การหยุดและเริ่มใหม่** เคารพ Retry-After เมื่อเจอ 429 จำกัดความถี่การลองใหม่ตามแหล่ง หยุดงานที่เกี่ยวข้องเมื่อพบหน้าให้ล็อกอิน/ยืนยันตัวตน ขาดสิทธิ์ หรือสิทธิ์หมดอายุ และให้ผู้ใช้ดำเนินการในโปรไฟล์เฉพาะ เมื่อกลับมาตรวจได้ให้บันทึกเวลาที่เริ่มใหม่ ช่วงเวลาที่หายยังอยู่ในประวัติ

**นโยบายเริ่มต้นที่ปรับได้หลังวัดโหลด** ตั้งได้สูงสุด 10 โพสต์เร่งรอบพร้อมกันทั้งระบบ เป้าหมายครั้งละ 24 ชั่วโมง กำหนดงบคำขอและเพดานเวลาต่อกลุ่มตามขอบเขตสิทธิ์และผลทดลอง หักงบจากทั้ง discovery และ revisit ร่วมกัน ถ้ามีงานปกติและงานเร่งของโพสต์เดียวกันถึงกำหนดพร้อมกัน ให้ผลการตรวจครั้งเดียวตอบทั้งสองงาน

## 4. ความทนทานของคิวและหลักฐาน

- **งาน** สร้างหนึ่ง logical job ต่อประเภท เป้าหมาย และรอบเวลา ใช้ unique key กันงานซ้ำ Worker จองแถวที่ถึงกำหนดด้วย `FOR UPDATE SKIP LOCKED` ใน transaction สั้น บันทึก token และวันหมดอายุของ lease แล้ว commit ก่อนเปิดเบราว์เซอร์ ระหว่างทำงานต่ออายุ lease จบงานได้เฉพาะ token ปัจจุบัน เมื่อ process หยุดกลางทาง worker รอบใหม่ใช้คีย์เดิมลองซ้ำได้
- **ประวัติ** ทุก observation มีเวลาที่สังเกตจริงและเวลาต้นทางเมื่อมีหลักฐาน สร้างรายการการเปลี่ยนแปลงเมื่อค่าที่มีความหมายต่างจากค่าก่อนหน้า การลอง ingest ซ้ำใน logical capture เดิมให้ผลเช่นเดิม การตรวจตามนัดครั้งถัดไปที่ได้ค่าเดิมบันทึกความสดใหม่โดยไม่เพิ่มเหตุการณ์ “ปิดขาย” ซ้ำ การประมวลผลล่าช้าไม่เขียนทับสถานะที่มีหลักฐานใหม่กว่า
- **ไฟล์** จำกัดขนาดและตรวจชนิดภาพ ครอปเฉพาะสินค้า/บริเวณหลักฐานที่จำเป็น บันทึกใน staging บน volume เดียวกัน ตรวจ hash และเปลี่ยนชื่อไฟล์แบบ atomic ก่อนบันทึกรายการอ้างถึงไฟล์พร้อม observation ใน SQL transaction เก็บ source URL, capture time, สัดส่วน/ชนิดไฟล์ และ hash ของภาพที่จัดเก็บจริง เมื่อภาพขาดให้แสดงสาเหตุ เมื่อ SQL commit ล้มเหลวไฟล์ตกค้างให้เก็บกวาดหลัง grace period และตรวจว่าไม่มีแถวอ้างถึง
- **สถานะอ่านไม่ได้** ถ้าโพสต์หาย เปิดไม่ได้ หรือรูปโหลดไม่สำเร็จ ให้บันทึกการเข้าถึงครั้งนั้นต่างหากจากสถานะขายล่าสุด การสูญเสียหลักฐานภายหลังต้องส่งผลต่อการแสดงป้ายและความสามารถในการตรวจย้อนกลับ
- **AI หรือกราฟหยุด** ระบบยังบันทึกการพบโพสต์และหลักฐานได้ ให้ AI รับงานหลัง commit ผ่านคิว enrich แยกชนิด Worker ส่งคำขอ Ollama แบบ asynchronous จำกัดหนึ่งคำขอ เพื่อให้รอผลโมเดลโดยปล่อย browser loop ทำงานอื่นได้ มี timeout, retry จำกัดและแสดงงานค้าง ใช้ผลจากกฎที่มีหลักฐานได้ก่อน ค่าอนุมานที่ไม่ชัดเจนให้พักตรวจ

## 5. ค้นหา สถิติราคา และกราฟ

API อ่านจาก Postgres โดยใช้ดัชนีตาม source ID, seller ID, product variant, สถานะ, เวลาและราคา ให้เริ่มค้นรุ่นฮาร์ดแวร์ด้วยรหัสรุ่นและตาราง alias ที่ทีมตรวจได้ พิจารณาเพิ่มดัชนีข้อความหลังวัด query จริง MCP เรียก API แบบอ่านอย่างเดียวผ่านรายการคำสั่งจำกัด ส่งภาพตาม evidence ID เป็น image content หรือระบุเหตุที่ไม่สามารถแสดง จำกัดจำนวนผลและขนาดภาพต่อคำขอ

กราฟราคาชุดแรกคำนวณค่ากลางและการกระจายของ **ราคาประกาศขาย** ในรุ่นย่อย สภาพ และเงื่อนไขที่เทียบกันได้ หนึ่งประกาศเดิมที่ถูกตรวจซ้ำต้องไม่สร้างตัวอย่างใหม่ในสถิติ ออกรายงานจำนวนตัวอย่าง ขอบเขตเวลาและความครอบคลุมของกลุ่ม ตัดประกาศซ้ำที่ยืนยันได้และแยกรายการที่สรุปราคาไม่ได้ การพยากรณ์ราคาจะเริ่มเมื่อมีประวัติพอให้ทดสอบย้อนหลังแบบเลื่อนเวลาเทียบกับการใช้ค่ากลางรอบก่อน

ระยะกราฟใช้ transactional outbox ใน Postgres สร้าง event ID และ entity version ใน transaction เดียวกับข้อมูลหลัก Projector อ่าน event เพื่อสร้างความสัมพันธ์ผู้ขาย–ประกาศ–สินค้า–กลุ่มใน GenesisBlockDB จัดการเหตุการณ์ซ้ำ การล้างข้อมูล การประมวลผลไม่ทัน และ rebuild จาก SQL ได้ ทดสอบกับ API/รุ่นจริงก่อนเปิด หากกราฟล่าช้า หน้าแอปยังอ่านข้อมูลหลักและเวลาเดียวกับหลักฐานเดิม

## 6. การเข้าถึง ขอบเขตสิทธิ์ และการปฏิบัติการ

| ประเด็น | ข้อกำหนดนำไปปฏิบัติ |
|---|---|
| สิทธิ์แหล่งข้อมูล | วาง live adapter ไว้หลัง feature flag ที่ปิดเริ่มต้น เปิดเฉพาะแหล่งที่ได้รับอนุญาตให้เก็บอัตโนมัติจากแพลตฟอร์มและมีสิทธิ์เข้าถึงกลุ่ม ตรวจแยกว่าขอบเขตครอบคลุมรูป คอมเมนต์ ประวัติผู้ขาย และการแสดงผลใดบ้าง ระบบพัฒนาได้ด้วย fixture หรือข้อมูลที่ผู้มีสิทธิ์ให้ใช้ |
| Session และขอบเขตเว็บไซต์ | ให้โปรไฟล์เบราว์เซอร์อยู่ภายใต้ Windows account เฉพาะงาน จำกัด ACL, ห้ามนำ login state เข้า Git/log/LLM แยก URL ที่ใช้เปิดโพสต์จากลิงก์ในเนื้อหา ตรวจ origin ทุก navigation/redirect ประเด็น upstream #558 เกี่ยวข้องกับการส่ง credentials ต่อไปอีก origin ผ่าน Response.follow() |
| การเข้าถึงแอป | ค่าเริ่มต้นเฉพาะ localhost ของผู้ใช้บน PC ใช้ session สำหรับ UI และ credential แบบ read-only สำหรับ MCP ตรวจสิทธิ์กลุ่มซ้ำเมื่อเรียกภาพ แยกสิทธิ์แก้ตารางงาน อนุญาต mutation เฉพาะ origin ของแอปพร้อม CSRF protection การเปิดจากโทรศัพท์จริงผ่านเครือข่ายเป็น deployment เพิ่มที่ต้องมี HTTPS และการยืนยันตัวตน |
| การส่งข้อมูลให้ Agent | มองข้อความโพสต์และ OCR เป็นข้อมูลจากภายนอก ใช้โมเดลในเครื่องผ่าน Ollama โดยไม่มีสิทธิ์สั่งงานหรืออ่านไฟล์ ตรวจ schema และตรวจว่า evidence reference มีอยู่ก่อนบันทึก Agent ภายนอกเครื่องต้องได้รับสิทธิ์ส่งข้อมูลออกตามขอบเขตของแหล่งก่อนเชื่อม |
| ข้อมูลผู้ขายและหลักฐาน | เก็บตัวระบุของแพลตฟอร์มและชื่อแสดงผลเฉพาะที่จำเป็น แสดงแหล่งและช่วงเวลาที่พบ ลดการเก็บช่องทางติดต่อและข้อมูลผู้ซื้อ ครอปหรือปิดบังก่อนเผยภาพให้ผู้เรียก อ่านไฟล์ผ่าน API เท่านั้น ตั้ง private/no-store สำหรับข้อมูลส่วนบุคคลและภาพ Cache เฉพาะเปลือกแอปใน service worker |
| ลบและเพิกถอน | เมื่อสิทธิ์หมดอายุให้หยุดดึงและบังคับขอบเขตการอ่านที่ API ทันที กำหนด retention และงานลบให้ครอบคลุมต้นฉบับที่เก็บ ภาพ แท็ก ดัชนี กราฟ และสำเนาสำรอง เก็บรายการลบแบบไม่มีเนื้อหาเพื่อประมวลผลซ้ำหลัง restore |
| สุขภาพระบบ | log รันตาม run ID, adapter version, result/reason และเวลาที่ใช้ แสดงคิวล่าช้า ช่องว่างการตรวจ อัตราภาพสำเร็จ พื้นที่ว่าง และเวลาของ backup ล่าสุดในหน้าจัดการ |

**งบเริ่มวัดบน i7-8700K / RAM 32 GB / RTX 3060 12 GB** ใช้ browser concurrency 1 และ AI concurrency 1 โมเดลแรกที่เสนอให้ทดลองคือ `qwen3:4b` ผ่าน Ollama ให้ผลทดสอบข้อความประกาศไทยเป็นตัวตัดสิน เปรียบเทียบเวลาต่อโพสต์ ความถูกต้องและ VRAM ก่อนล็อกรุ่น กำหนดเพดานเวลาและจำนวนโพสต์ต่อรอบ ทดสอบขณะที่แอปเปิดดูสินค้าและมีงาน 5 กลุ่ม หากระยะเวลารอบจริงเริ่มเกินตาราง ให้ลดส่วนงานติดตามเสริมและ inference ก่อน เพิ่มความถี่ภายใต้ขอบเขตสิทธิ์เมื่อวัดภาระแล้ว ขนาดคลังภาพต่อวันประมาณได้จากจำนวน **ภาพใหม่ที่เก็บจริง × ขนาดภาพหลังแปลงเฉลี่ย** และต้องรวมพื้นที่สำรองแยกต่างหาก

**สำรองและกู้คืน** ตั้งงานทุกวันหลังหยุดการเขียนชั่วคราว ทำ pg_dump พร้อม manifest ของภาพที่มีใน DB คัดลอกภาพตาม hash และเก็บชุดที่เข้ารหัสแยกจากดิสก์ทำงาน เก็บค่า configuration และเวอร์ชัน migration โดยแยก secrets ออกจากชุดส่งออก ทดสอบ restore ไปยังไดเรกทอรีและฐานสำรอง ตรวจ orphan/hash และสุ่มเปิดรายการพร้อม timeline และรูปผ่าน API ก่อนนำระบบกลับมาใช้ ให้แสดงเวลาสำรองสำเร็จล่าสุดจริงหากเครื่องปิดช่วงนัด เก็บชุดรายวัน 7 ชุดและรายสัปดาห์ 4 ชุด ปลายทางต้องเป็นดิสก์อื่นที่ไม่ใช่ดิสก์ทำงาน กำหนด path ตอนติดตั้งและไม่บันทึกไว้ในรีโป เก็บกุญแจเข้ารหัสนอกชุดสำรอง ([Issue #42](https://github.com/Freshair129/paiya/issues/42))

## 7. เงื่อนไขเปิดใช้แต่ละส่วน

| ขั้น | หลักฐานที่ต้องมี |
|---|---|
| MVP จาก fixture | ทดสอบครบตั้งแต่นำเข้าถึงแอป/MCP ด้วยโพสต์ภาษาไทยและภาพจำลอง รวมผู้ขายชื่อซ้ำ จองโดยผู้ซื้อ ยกเลิกจองหลายรอบ โพสต์หลายชิ้น ข้อมูลไม่ครบ และเวลาสังเกตย้อนลำดับ |
| ทดลองนำเข้าเอง (M) | ให้ผู้ซื้อส่งข้อความพร้อมลิงก์ในขอบเขตที่ใช้ได้ ทวนตัวอย่างก่อนบันทึก เปิดที่มาของสถานะและยอดเทียบ ทดสอบการเพิกถอน/ลบ รวมถึงการเปิดจากมือถือผ่าน HTTPS วัดประโยชน์ตาม [แผนตรวจรับ](../quality/buyer-acceptance.md) |
| Live pilot (B) | ยืนยันสิทธิ์รวบรวมและใช้ข้อมูลตามขอบเขต ทดสอบ dummy credentials กับสอง origin ทั้งลิงก์และ redirect โดยข้อมูลรับรองต้องไม่ส่งข้าม ทดสอบเรียงล่าสุดและจับคู่โพสต์–ผู้ขายกับรายการที่มนุษย์เห็นในช่วงเวลาเดียวกัน ทดสอบเว็บขอ login, 429 และ DOM เปลี่ยนก่อนเปิดใช้ห้ากลุ่ม |
| ความต่อเนื่อง | ปิด worker หลังบันทึกภาพและหลัง commit แล้ว replay ตรวจว่าไม่มีรายการ/เหตุการณ์ซ้ำ จำลองเครื่องหลับและยืนยันช่วงขาด ทดสอบ restore และตรวจสิทธิ์ทั้ง UI กับ MCP |
| เปิดใช้งาน (C) | ผ่านเงื่อนไขของส่วนที่จะเปิดในตารางนี้ งาน O1–O4 และประตู C1 ใน [แผนส่งมอบ](../delivery/ROADMAP.md) รุ่นแรกผูก `127.0.0.1` บน PC ของเจ้าของ |
| ส่วนขยาย | เพิ่ม MinIO เมื่อมีความต้องการใช้อ็อบเจกต์ข้ามเครื่อง เพิ่ม GenesisBlockDB เมื่อทดสอบ outbox/rebuild/deletion ผ่าน และเปิดพยากรณ์เมื่อข้อมูลผ่านเกณฑ์ใน SRS |

**สถานะการพิสูจน์ ณ วันที่เอกสาร** ทีมยังต้องทดสอบ Facebook Groups ที่ได้รับอนุญาตจริง ความถูกต้องของการแยกข้อมูล ประสิทธิภาพของโมเดลไทยบนเครื่อง และการกู้คืนครบทั้ง SQL กับรูป โครงสร้างด้านบนเป็นข้อกำหนดและแบบทดสอบสำหรับนำไปสร้าง
