# สารบัญเอกสาร ป้ายยา (paiya)

เริ่มจากความต้องการของผู้ซื้อใน PRD แล้วเปิด SRS เพื่อดูข้อกำหนดที่ต้องทำและวิธีตรวจรับ ใช้สเปกสถาปัตยกรรมเมื่อต้องเลือกส่วนของระบบที่รับผิดชอบการเปลี่ยนแปลงนั้น

| เอกสารหลัก | ตอบคำถาม | ผู้ดูแลตามบทบาท |
|---|---|---|
| [Product Requirements](product/PRD.md) | ผู้ใช้ต้องทำอะไรได้ ขอบเขตและลำดับความสำคัญคืออะไร | Product owner |
| [Architecture Specification](architecture/SPEC.md) | Collector, API, ฐานข้อมูล, ไฟล์ภาพ และ AI ทำงานร่วมกันอย่างไร | Tech lead |
| [Software Requirements](requirements/SRS.md) | ข้อมูลเข้าออกเป็นหน้าตาแบบใด ระบบตอบสนองอย่างไร และตรวจรับอะไร | Engineering + QA |
| [Requirements Traceability](quality/TRACEABILITY.md) | แต่ละความต้องการอ้างกลับไปยังข้อกำหนดและชุดทดสอบใด | QA |
| [Delivery Roadmap](delivery/ROADMAP.md) | เริ่มงานใดได้ก่อน งานใดต้องรอ และส่งหลักฐานอะไร | Delivery lead |
| [ADR 0001 ฐานข้อมูลหลักและการติดตามด้วยหลักฐาน](architecture/decisions/0001-observation-store.md) | เหตุใดจึงเลือก PostgreSQL กับคลังภาพบนเครื่อง และเมื่อใดควรทบทวน | Tech lead |

### วิธีดูแลเอกสาร

- เปลี่ยนความสามารถหรือเกณฑ์รับงาน ให้แก้เอกสารเจ้าของเรื่องก่อน แล้วตามรหัสไปอัปเดตเอกสารที่ได้รับผลและตารางตรวจย้อนกลับใน PR เดียวกัน
- คงรหัสข้อกำหนดเดิมเมื่อย้ายหัวข้อ หากเลิกใช้ให้บันทึกว่าถูกแทนด้วยข้อใด เพื่อให้ Issue และผลทดสอบเก่ายังอ่านรู้เรื่อง
- เมื่อเพิ่มเอกสารใต้ `docs/` ให้เพิ่มลิงก์ในหน้านี้ด้วย ก่อนส่ง PR ให้รัน `python scripts/check_docs.py` จากรากรีโป
- ผลการทดสอบให้ระบุ commit ชุดข้อมูลและคำสั่งที่ใช้ใน PR เมื่อมีผลแล้วจึงเปลี่ยนสถานะ coverage รายข้อ ดูขั้นตอนที่ [คู่มือผู้ร่วมพัฒนา](../CONTRIBUTING.md)
