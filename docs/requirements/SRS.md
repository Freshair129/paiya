# ป้ายยา (paiya) · Software Requirements Specification

เวอร์ชัน 0.2 · 7 พฤศจิกายน 2026 · ข้อเสนอสำหรับพัฒนาและตรวจรับ

## 1. ขอบเขตและสัญญาระหว่างส่วนประกอบ

ใช้ PC หนึ่งเครื่องเป็นคลังส่วนตัวของผู้ซื้อหนึ่งคน ระยะ A รับข้อมูลสังเคราะห์ ระยะ M รับลิงก์และข้อความที่ผู้ซื้อส่งภายใต้ขอบเขตสิทธิ์ ระยะ B เพิ่มงานเก็บอัตโนมัติได้สูงสุด 5 กลุ่มหลังผ่านเงื่อนไขของแหล่ง เป้าหมายค้นพบโพสต์วัดเฉพาะระยะ A/B จากโพสต์ที่โหลดให้เห็นจริง ส่วน M วัดขั้นตอนเก็บหลักฐานและเปรียบเทียบดีลตาม PRD

| ส่วน | เทคโนโลยีและความรับผิดชอบ |
|---|---|
| นำเข้าด้วยมือ | PWA ส่งข้อความ ลิงก์ และภาพที่อนุญาตไปยัง FastAPI ในเครื่อง ให้ผู้ซื้อดูตัวอย่างก่อนบันทึก ใช้กฎเดียวกับข้อมูลอัตโนมัติในการยืนยันราคา ผู้ขาย และสถานะ |
| Collector | Python + Scrapling ควบคุม Chromium หนึ่ง browser profile แยกเฉพาะงาน ทดสอบ adapter กับ fixture ก่อนเปิดใช้บนแหล่งจริง ตัว adapter ส่ง observation เป็น JSON ที่มี schema version |
| Scheduler + worker | Python ใช้คิวงานใน PostgreSQL 17 เริ่มด้วยหนึ่ง browser job พร้อมกัน งานค้นโพสต์ใหม่กับงานตรวจ permalink มีเวลานัดหมายแยกกัน |
| System of record | PostgreSQL 17 เก็บ observation, facts, สถานะปัจจุบัน และ metadata ของหลักฐาน รูป WebP/JPEG อยู่ใน private filesystem และดึงผ่าน API |
| Enrichment | Ollama ในเครื่อง รับข้อความเท่าที่จำเป็น เสนอ tags หรือ facts พร้อม span อ้างอิง ใช้ rule-based parser กับจำนวน ราคา และสถานะที่อ่านได้ชัดเจนก่อน |
| Query | FastAPI ทำหน้าที่ตรวจสิทธิ์และอ่าน SQL สำหรับ React mobile PWA และ MCP แบบ stdio ทั้งสองช่องทางใช้ read model เดียวกัน |
| ระยะต่อไป | GenesisBlockDB รับ graph projection จาก SQL ผ่าน outbox เมื่อมี use case ที่ผ่านเกณฑ์ในข้อ 8 |

## 2. ข้อกำหนดเชิงหน้าที่

| รหัส | พฤติกรรมที่ระบบต้องทำได้ | เชื่อม PRD |
|---|---|---|
| FR-01 | ผู้ใช้เพิ่ม แก้รอบ 30 หรือ 60 นาที ดูผลตรวจล่าสุด และพักกลุ่มได้ ก่อนเริ่มงานต้องพบ grant ที่ยังใช้ได้และอนุญาตชนิดการเก็บที่ร้องขอ | PR-01, PR-09 |
| FR-02 | ทุก discovery run ตรวจ session, กลุ่มปลายทาง และสัญญาณยืนยันการเรียงโพสต์ล่าสุดจาก UI ถ้ายืนยันไม่ได้ให้บันทึก partial พร้อมเหตุผล เก็บหลักฐานได้ตามขอบเขตสิทธิ์ แต่ไม่เลื่อน checkpoint ความครอบคลุม | PR-02 |
| FR-03 | อ่านโพสต์ที่โหลดพร้อมบันทึกขอบเขตการเลื่อน จำนวนที่พบ ข้อจำกัด และช่วงเวลางาน ใช้ stable key กับ overlap ของโพสต์ที่เคยพบเพื่อรับมือการปักหมุดและการเรียงใหม่ เมื่อชนงบเวลาหรือจำนวน scroll ก่อนถึง overlap ให้บันทึก partial | PR-02 |
| FR-04 | มีรายการ Watch สำหรับเปิดตรวจ permalink โดยตรง เมื่อผู้ใช้เปิดการติดตามถี่ให้เสนอรอบ 10 นาที จำกัดจำนวนและอายุ เช่น MVP เริ่ม 10 permalink รวมและหมดอายุใน 24 ชั่วโมง ผู้ใช้ลบหรือเปิดใหม่ได้ ระบบต้องรายงานเวลาจริงเมื่อคิวตรวจไม่ทัน | PR-03, PR-06 |
| FR-05 | บันทึก observation ทุกครั้งที่ตรวจสำเร็จแม้เนื้อหาซ้ำ แยกเวลาลองตรวจล่าสุด เวลาที่อ่านข้อมูลสำเร็จ และเวลาที่เห็นหลักฐานสถานะ การเห็นโพสต์เดิมซ้ำสร้างเหตุการณ์ใหม่เฉพาะเมื่อข้อเท็จจริงเปลี่ยน | PR-02, PR-03 |
| FR-06 | แยกสถานะการขายของแต่ละรายการ สถานะการเข้าถึงโพสต์ และความสดของหลักฐาน ระบุผู้พูดและ coverage ตามข้อ 4 ตรวจให้บทบาทในหลักฐานตรงกับเจ้าของคอมเมนต์ที่อ้าง และยืนยันว่าเป็นผู้ขายในโพสต์นั้นก่อนใช้คำพูดยืนยันจองหรือขายแล้ว | PR-03 |
| FR-07 | ผูกข้อความและรูปสินค้าหรือภาพ crop เข้ากับ observation และโพสต์ เปิดเทียบกับ permalink ได้ ถ้าไม่มีภาพต้นทางหรือเก็บไม่สำเร็จให้แสดงเหตุผลและ evidence ข้อความที่มี | PR-04 |
| FR-08 | Seller Profile แสดงเวลาที่ระบบพบครั้งแรก กลุ่มที่เห็น ประวัติประกาศที่แยกซ้ำแล้ว และจำนวนประกาศที่มีหลักฐานปิดขาย ทุกตัวเลขย้อนดูรายการได้ การรวมข้ามกลุ่มต้องยืนยัน stable identity และแสดงเฉพาะกลุ่มที่ผู้ใช้ยังมีสิทธิ์อ่าน | PR-05, PR-09 |
| FR-09 | หน้าแรกเป็น feed สินค้า ค้น/กรองตามรุ่น ราคา กลุ่ม สถานะ และ tags ได้ แตะเปิดประกาศ ประวัติผู้ขาย หลักฐาน และ Watch ได้บนจอมือถือ | PR-06 |
| FR-10 | Local AI บันทึก model version, หลักฐาน, span, ผล validate และ confidence ทุกข้อเสนอ ตัวเลขและสถานะบน UI ต้องมาจาก fact ที่ผ่านกฎยืนยัน ใช้งานค้นหาและติดตามต่อได้เมื่อ Ollama หยุด | PR-07 |
| FR-11 | MCP ค้นโพสต์ ดูรายละเอียด ประวัติผู้ขาย ราคา และเรียกภาพตาม evidence ID ได้ผ่านสิทธิ์อ่านชุดเดียวกับ UI รองรับ Markdown สำหรับคนอ่านและ JSON เป็นข้อมูลหลัก | PR-04, PR-07 |
| FR-12 | แสดงแนวโน้มราคาตั้งขายพร้อมวันที่ window, จำนวนตัวอย่าง, สกุลเงิน และเกณฑ์เทียบรุ่น/สภาพตามข้อ 8 | PR-08 |
| FR-13 | ตรวจ grant ก่อนเก็บ ก่อนบันทึกผล และก่อนส่งรูปหรือข้อมูลกลับ การเพิกถอนหยุดคิวงานพร้อมปิดการอ่านที่เกี่ยวข้อง การลบมี job, บันทึกผล และทดสอบผลใน SQL, ไฟล์ และข้อมูลอนุพันธ์ | PR-09 |
| FR-14 | รับ permalink ตรงและข้อความที่ผู้ซื้อส่งภายใต้สิทธิ์สำหรับการนำเข้าด้วยมือ ตรวจขอบเขตแหล่งกับสิทธิ์ทั้งตอนแสดงตัวอย่างและตอนยืนยัน แนบภาพเป็นหลักฐานเมื่ออนุญาต แสดงข้อเท็จจริงที่สกัดได้พร้อมบรรทัดอ้างอิง การยืนยันเท่านั้นที่สร้าง observation ระบบไม่ส่งคำขอไปยัง URL ต้นทาง และแยกเวลาที่ผู้ใช้ส่งออกจากเวลาโพสต์ | PR-10 |
| FR-15 | เก็บกฎตั้งรับของผู้ซื้อ ตรวจรายชิ้นด้วยรุ่นและคุณลักษณะที่มีหลักฐาน นำราคาเสนอขายต่อชิ้นสกุลบาทมาเทียบกับงบ ราคาที่เท่ากับเพดานยังเข้าเกณฑ์ เปรียบเทียบหลังตัดตัวเลือกที่กฎห้าม สร้างผลในกล่องแจ้งเตือนพร้อมเงื่อนไขที่ตรง ชิ้นสินค้า เวลา และหลักฐานราคา ตามกติกาการเปลี่ยนสถานะด้านล่าง | PR-11 |
| FR-16 | Watch ระบุโพสต์และชิ้นภายในโพสต์ได้ เมื่อเลือกชิ้นให้แจ้งเฉพาะการเปลี่ยนแปลงของชิ้นนั้น เปิดดูหลักฐานที่ทำให้สถานะเปลี่ยนได้ งานตรวจ permalink เดียวกันในรอบเดียวใช้ร่วมกันทุก Watch โพสต์ที่มาจากการส่งเองอัปเดตจาก observation ถัดไปโดยไม่สร้างงานเปิดลิงก์ | PR-12 |
| FR-17 | เทียบชิ้นสินค้าที่ต่างกัน 2–3 ชิ้นตามสิทธิ์ปัจจุบัน แสดงราคาและหน่วย ค่าส่งที่ใช้กับชิ้นนั้น ยอดรวม สกุลเงิน สภาพ ข้อความประกัน ผู้ประกาศ สถานะ เวลาและหลักฐานที่รองรับแต่ละค่า เก็บราคาเสนอขายกับค่าส่งเป็นคนละข้อเท็จจริงของชิ้นหรือข้อเสนอ | PR-13 |

**รอบอัตโนมัติของ FR-03/04** สำหรับแหล่งที่มีสิทธิ์เก็บอัตโนมัติ โพสต์ใหม่ที่ยังไม่ยืนยันปิดขายมีสิทธิ์เข้าคิว revisit ตามรอบของกลุ่มใน 24 ชั่วโมงแรก หมุนตรวจจากรายการที่เกินกำหนดนานที่สุด จำกัดด้วยงบร่วมของกลุ่ม เมื่อหมดช่วงดังกล่าวให้ปรับข้อมูลเมื่อพบใหม่ในฟีดหรือเมื่อผู้ใช้ติดตามต่อ การบันทึกรายการโปรดคงอยู่จนยกเลิก ส่วนการเร่งตรวจทุก 10 นาทีมีเพดานและวันหมดอายุแยกกัน

**การรับข้อมูลด้วยมือ (FR-14)** ลิงก์หรือตัวระบุกลุ่มที่ตีความไม่ได้ให้ขอ permalink ตรงก่อนยืนยัน ส่งคำขอเดิมซ้ำด้วยคีย์เดิมและเนื้อหาเดิมต้องคืนผลเดิม การใช้คีย์เดิมกับเนื้อหาที่เปลี่ยนต้องปฏิเสธ ผู้ซื้อตั้งใจส่งรอบใหม่ให้ผูกโพสต์เดิมภายในขอบเขตเดิม และสร้างเหตุการณ์ธุรกิจเฉพาะเมื่อข้อเท็จจริงเปลี่ยน ข้อความที่คัดลอกมาและภาพที่ผู้ใช้แนบเพียงลำพังไม่ยืนยันว่าใครเป็นผู้ขาย รูปเก็บเป็นหลักฐานที่เปิดดูได้ รุ่นนี้ใช้ข้อความสำหรับสกัดข้อมูล

**วงจรของกฎตั้งรับ (FR-15)** การสร้าง แก้ หรือเปิดกฎที่พักไว้ใช้ผลปัจจุบันเป็นจุดเริ่มต้น ผู้ซื้อเปิดดูผลเดิมได้โดยไม่เกิดแจ้งเตือนย้อนหลัง หลังจากนั้นให้แจ้งเมื่อพบชิ้นที่ตรงเป็นครั้งแรก หรือกลับมาตรงหลังมีข้อเท็จจริงยืนยันว่าเคยหลุดเงื่อนไขแล้ว ข้อมูลที่ยังขาด เช่น ข้อความระบุเพียง “3060” เมื่อผู้ใช้เจาะจง 12GB ให้คงความไม่แน่ใจ การขาดข้อมูลจะไม่ล้างสถานะจนส่งแจ้งเตือนเดิมซ้ำ งานซ้ำหรืองานเก่าที่เสร็จช้าต้องไม่สร้างการเข้าเงื่อนไขใหม่ การพักกฎหยุดแจ้งเตือน และการเปิดกล่องแจ้งเตือนต้องตรวจสิทธิ์ล่าสุดของหลักฐานด้วย

**ราคารวมเมื่อเทียบดีล (FR-17)** ถ้าผู้ขายระบุราคาต่อชิ้นและค่าจัดส่งสำหรับการรับแบบเดียวกัน ให้รวมสองยอดที่สกุลเงินตรงกัน ถ้ามีหลักฐานว่าส่งฟรีหรือรวมส่ง ให้ใช้ยอดตามประกาศเพียงครั้งเดียว ถ้าค่าส่งไม่ปรากฏ เป็นยอดรวมหลายชิ้นที่แบ่งรายชิ้นไม่ได้ หรือราคายังเป็นช่วง ให้แสดงส่วนที่ทราบพร้อม “ยังไม่ทราบยอดรวม” ห้ามนำมัดจำ ค่างวด หรือยอดเสนอซื้อมาใช้แทนราคาสินค้า หน้าตั้งรับแสดงให้ชัดว่าเพดานงบใช้ราคาเสนอขายต่อชิ้น ส่วนหน้าราคาแนวโน้มใช้กติกาข้อ 8


## 3. ข้อมูลหลักและกฎระบุตัวตน

[แบบจำลองข้อมูล](../architecture/data-model.md) กำหนดคีย์ ความสัมพันธ์ และดัชนีที่ใช้สร้าง migration ส่วน [ERD](../architecture/views/erd.md) แสดง cardinality ระหว่างการนำเข้า หลักฐาน ข้อเท็จจริงรายชิ้น และการแจ้งเตือน ตารางนี้สรุปกฎพฤติกรรมที่ระบบต้องคงไว้

รหัสหลักของกลุ่ม โพสต์ ชิ้นสินค้าและหลักฐานใช้ UUID ภายใน เก็บ timestamp ใน UTC และแสดงตาม Asia/Bangkok เวลาที่ต้นทางระบุว่า “5 ชั่วโมงที่แล้ว” ให้เก็บข้อความต้นทางพร้อมความละเอียดหรือเวลาประมาณแยกจากเวลาตรวจจริง

| Entity | ฟิลด์และข้อบังคับหลัก |
|---|---|
| source_grants, groups | grant ผูก group_id ของแหล่ง กำกับชนิดการนำเข้า ขอบเขต read/capture/media/comments/seller_history/analytics/agent_export ประวัติสิทธิ์ และอายุจัดเก็บ กลุ่มเก็บ canonical URL กับการตั้งรอบตรวจเมื่อมีสิทธิ์อัตโนมัติ การลงชื่อเข้าใช้สำเร็จอย่างเดียวไม่สร้าง grant |
| jobs, capture_runs | คิวงานกำหนดรอบนัดและ lease งานที่รับข้อมูลมีรหัสรอบ กลุ่ม ชนิดแหล่ง สิทธิ์ และเวลารับ ชุดผลการตรวจ session และ sort ใช้กับงานเปิดหน้าอัตโนมัติ การปลุกเครื่องหลัง sleep รวมงานที่พลาดเป็นรอบชดเชยและบันทึกช่วง gap |
| sellers, posts | seller มี source + identity_scope + external_actor_key ไม่ซ้ำภายใน scope โพสต์มี group_id + source_post_key ไม่ซ้ำ, permalink, seller_id ที่ว่างได้ และ posted_at ต้นทาง ชื่อเหมือนกันไม่เพียงพอต่อการผูกรายบุคคล |
| observations | capture_id คงเดิมตลอดการ retry งานเดียวกัน มี post_id, run_id, observed_at, source_time/precision, parser_version, payload_hash, normalized_json, status ของการเข้าถึงและ coverage ฟิลด์ที่ไม่เห็นเก็บ null ห้ามแทนศูนย์ |
| listing_items, price_facts | หนึ่งโพสต์มีหลายรายการได้ เก็บ SKU/รุ่นย่อย, condition, bundle/unit, item key ภายในโพสต์ ราคาเก็บ numeric, currency, price_kind, ช่วงหรือจำนวน, evidence_id, item_id ถ้าแยกรายการไม่ได้ให้เก็บเป็น bundle หรือ unresolved |
| comments, comment_versions | stable comment key เท่าที่มี, post_id, parent_id, source/observed_at, role, actor_key ตาม grant, ข้อความที่จำเป็นและ version การพบซ้ำ ปรับหรือลบเฉพาะเมื่อมีหลักฐาน การไม่พบในหน้าที่โหลดบางส่วนไม่ใช่การลบ |
| evidence, media_assets | evidence_id, post_id, observation_id, item_id ถ้ารู้, grant_id, permalink, source_span, role, captured_at, media_asset_id หรือเหตุผลภาพขาด media_asset มี opaque storage key, sha256, MIME, width, height และ bytes |
| sale_events, current_items | event มี item_id, observation_id, fact_key, normalized status, effective_at/precision, evidence_id, rule_version และผลการทวนสอบ current_items เป็น projection ที่สร้างใหม่ได้ ต้องชี้ event/evidence ซึ่งใช้ตัดสิน |
| buy_rules, rule_item_states, alerts | กฎเก็บตัวกรองกับงบต่อชิ้น สถานะการตรงกฎผูกคู่กฎและชิ้น กล่องแจ้งเตือนผูกเหตุการณ์และหลักฐานเพื่อกันซ้ำและตรวจสิทธิ์ขณะอ่าน |
| watches, tags, purge_jobs | Watch ผูก post_id กับ item_id เมื่อเลือกเฉพาะชิ้น และเก็บเวลาบันทึกกับอายุเร่งตรวจสำหรับแหล่งอัตโนมัติ ส่วน tags ผูก entity + evidence และ rule/model version งานลบเก็บ scope, เวลา และผลตรวจว่าข้อมูลอนุพันธ์ถูกจัดการ |

ตัวอย่าง constraints สำหรับ migration จริง โดยตัว scheduler กำหนด run_id เดียวตลอดการ retry ของรอบนั้น

```sql
CREATE UNIQUE INDEX posts_source_key
  ON posts (group_id, source_post_key);
CREATE UNIQUE INDEX observations_one_per_capture
  ON observations (run_id, post_id, capture_id);
CREATE UNIQUE INDEX sale_events_one_per_fact
  ON sale_events (observation_id, item_id, fact_key);
```

นิยาม timeline ของโพสต์ให้รวม sale_events, price_facts และการเปลี่ยนแปลงคอมเมนต์จาก comment_versions เรียงตามเวลาที่ตรวจพบพร้อมเวลาต้นทางเมื่อยืนยันได้ คอมเมนต์ใหม่ที่มี stable key เกิดเหตุการณ์ครั้งเดียว การแก้ไขสร้าง version ใหม่ การเห็นยอดรวมเพิ่มจาก 5 เป็น 7 โดยยังอ่านตัวข้อความไม่ได้ให้สร้างเพียง comment_count_changed พร้อมค่าก่อน–หลัง ห้ามสร้างคอมเมนต์หรือผู้เขียนสมมติ

Foreign key ของ evidence ต้องบังคับให้ observation และโพสต์อยู่คู่กัน และ grant อยู่กับกลุ่มเดียวกับโพสต์ การเลือก candidate จาก adaptive selector ห้ามสร้างการเชื่อมคนหรือสินค้าโดยลำพัง หากขาด stable post key ให้พักผลพร้อมสาเหตุและนับในสถิติ parser failure กรณีขาด seller identity ยังคงโพสต์เป็น unknown seller ได้

โพสต์ข้ามกลุ่มเก็บคนละ permalink ใช้ offer cluster แยกต่างหากเมื่อมีหลักฐานว่าเป็นประกาศเดียวกัน ภาพตรงกันหรือชื่อผู้ขายตรงกันเพียงอย่างเดียวไม่พอจับคู่ กรณีหลายรายการที่ผู้ขายแก้ลำดับให้เทียบ item key จากหลักฐาน หลีกเลี่ยงการจับคู่ด้วยลำดับ DOM เดิม

## 4. สถานะ การเปลี่ยนแปลง และช่วงข้อมูลขาด

| ข้อมูลที่เห็น | ผลที่บันทึก |
|---|---|
| ป้ายต้นทางที่ชัดเจน หรือข้อความเจ้าของที่ยืนยันตัวและระบุสินค้าได้ เช่น “3060 ขายแล้ว” | สร้าง event สำหรับรายการนั้น เก็บหลักฐานและเวลา อีกชิ้นในโพสต์คงสถานะตามหลักฐานของตน |
| ผู้ขายยืนยันว่า “ปล่อยต่อ หลุดจอง” | ให้ event ใหม่เปลี่ยน reserved กลับไป open เมื่อ scope และลำดับเวลาชัดเจน |
| ผู้ซื้อพิมพ์ “จอง” หรือผู้ขายพิมพ์ “ปิดจอง” โดยบริบทคลุมเครือ | เก็บ activity หรือ candidate ชวนตรวจ ยังไม่ยืนยันว่าขายแล้ว ถ้าหลักฐานยืนยันสองชิ้นขัดกันและเรียงไม่ได้ ให้ขึ้น needs_review พร้อมเหตุผล |
| อ่านได้แต่ไม่มีคำยืนยันสถานะ | sale_status เป็น unknown หากมีเพียงการอ่านครั้งแรก แสดง “ยังไม่พบข้อความปิดขาย ณ …” หากมีสถานะยืนยันเดิม แสดงเวลาหลักฐานนั้นแยกจากเวลาตรวจล่าสุด |
| ไม่พบโพสต์, ลิงก์เปิดไม่ได้, session หมดอายุ หรือ CAPTCHA | บันทึก access เช่น unavailable, permission_denied หรือ session_required พร้อมเวลา พักเมื่อมีอุปสรรคด้านสิทธิ์หรือการยืนยันตัวตน เก็บสถานะขายก่อนหน้ากับเวลาเดิม |
| FB แสดง 5 ความคิดเห็น แต่โหลดได้ 2 ข้อความของคนเดียว | เก็บ source_reported_comment_count=5, distinct_comments_seen=2, distinct_known_commenters_seen=1, coverage=partial ชื่อที่ยืนยันไม่ได้ไม่นำมานับเป็นคนไม่ซ้ำ |

เมื่อหลักฐานจากคอมเมนต์ระบุบทบาทต่างจากคอมเมนต์ที่อ้าง หรือระบุตัวผู้พูดเป็นคนละคนกับผู้ขายของโพสต์ ให้กันหลักฐานนั้นออกจากการยืนยันสถานะและบันทึกสาเหตุ คำยืนยันต้องชี้ถึงชิ้นสินค้าที่ระบุได้ในโพสต์เดียวกัน การเลือกบทบาทเองในหน้าส่งข้อมูลไม่สร้างหลักฐานตัวตน

ค่า sale_status ที่อนุญาตคือ unknown, open, reserved, sold, withdrawn ส่วน needs_review เป็น flag ของการตีความ คำว่า sold ในแอปหมายถึงพบป้ายหรือการแจ้งปิดขายที่ยืนยันแหล่งได้ การแสดงระดับโพสต์หลายชิ้นใช้ “ขายแล้ว 1 จาก 3 รายการ” เมื่อทราบสถานะครบถ้วนตามที่แสดง

งานหนึ่งเขียน observation, facts และ current projection ผ่านธุรกรรมต่อเนื่องหรือคิวที่ replay ได้ อ่านซ้ำ A→A บันทึกเวลาตรวจทั้งสองครั้งและมี change event ครั้งเดียว เปลี่ยน A→B→A ต้องได้ประวัติสามสถานะ งานเก่าที่เสร็จช้าเพิ่มหลักฐานย้อนหลังได้โดยไม่ทับข้อเท็จจริงใหม่กว่า

กรณีตรวจ 09.00 น. และ 09.30 น. หากเกิดการจองแล้วถอนระหว่างนั้น ระบบรู้ได้เฉพาะข้อมูลที่ยังเห็นหรือมี timestamp ต้นทาง สถานะที่ข้อมูลต้นทางขัดกันให้เปิดดูข้อขัดแย้งและงดแสดงป้ายยืนยันสำหรับสถานะปัจจุบัน เก็บช่วงระหว่างหลักฐานสองชิ้นเมื่อรู้เพียงว่ามีการเปลี่ยนผ่านในช่วงนั้น UI แสดงเวลาถัดไป สถานะ stale เมื่อพ้นรอบโดยยังไม่มีผลสำเร็จ และเหตุผลกรณีตรวจไม่ได้

## 5. สัญญาของ collector และ API

รูปแบบ JSON และ envelope ที่ใช้รับ observation รวมถึง HTTP endpoints และเครื่องมือ MCP สำหรับอ่านข้อมูล อยู่ใน [สัญญาข้อมูลของ Collector และช่องทางค้นคืน](../architecture/contracts/collector-and-query.md) สัญญา observation v1 ที่ใช้ตรวจ fixture ปัจจุบันรับชนิด fixture และ facebook_live ส่วน [สัญญาการนำเข้าและการซื้อ](../architecture/contracts/buyer-workflows.md) ระบุแบบเสนอสำหรับ manual import กฎตั้งรับ กล่องแจ้งเตือน Watch รายชิ้น และการเทียบดีล ใช้เกณฑ์ข้อ 7 ตรวจการคืนหลักฐาน การเล่นข้อมูลซ้ำ และการเพิกถอนสิทธิ์

## 6. สิทธิ์ การลบ และการดูแลระบบ

ระบบเริ่มจาก loopback และเก็บ browser profile แยกจากข้อมูล export หน้า PWA ใช้ session ที่ตรวจสิทธิ์กับ API ส่วน MCP ใช้ credential แบบอ่านอย่างเดียว เมื่อจะเปิดให้มือถือเครื่องอื่นใน LAN ต้องเปิดการยืนยันตัวตนและ HTTPS ก่อน session cookies, password และ authorization header ห้ามอยู่ใน JSON ที่เก็บ log, prompt หรือ Git

ตรวจ grant ของแหล่งและอายุจัดเก็บสำหรับการนำเข้าด้วยมือด้วย สิทธิ์นำเข้าเองไม่ให้สิทธิ์ระบบเปิดแหล่งนั้นตามเวลา และข้อมูลการตั้งรับของผู้ซื้อให้เข้าถึงได้ภายใต้ session เจ้าของเครื่องเท่านั้น เมื่อสิทธิ์อ่านถูกถอนให้ซ่อนผลกฎ ข้อมูลในกล่องแจ้งเตือน ผลเทียบ และภาพที่อ้างถึงข้อมูลนั้นก่อนงานลบตามขอบเขต

กำหนดอายุเก็บต่อแหล่งก่อนเปิดเก็บตามขอบเขตที่ได้รับอนุญาต เมื่อครบอายุให้เข้าคิวลบอัตโนมัติ การแสดงข้อมูลใน MCP สำหรับโปรแกรมที่ส่งบริบทไปยังโมเดลภายนอกต้องมีสิทธิ์ agent_export ครอบคลุมปลายทางนั้น ค่าเริ่มต้นอนุญาตเฉพาะ harness/โมเดลในเครื่อง กลุ่มที่มีสิทธิ์อ่านในแอปอย่างเดียวไม่ส่งผลออกผ่าน MCP

เก็บเฉพาะข้อความประกาศและคอมเมนต์ที่เกี่ยวกับสถานะตาม grant รวมถึงภาพ crop ที่เห็นสินค้า หากเก็บ thumb ซ้ำตาม content hash แต่ละ reference ต้องมีสิทธิ์ของตน การเพิกถอนปิดการอ่านและหยุดงานทันที จากนั้นงานลบจัดการ facts, ข้อความ, ภาพที่ไม่มี reference เหลือ และ caches ตาม scope ที่สั่ง สร้างสถิติผู้ขายและราคาขึ้นใหม่จากข้อมูลที่ยังอนุญาต ห้าม service worker cache หลักฐานส่วนตัวแบบถาวร การกู้ backup ต้อง replay รายการลบก่อนเปิดให้ค้น

บันทึก structured log สำหรับ run_id, เวลารอคิว, session/sort/parser error, coverage, อายุหลักฐาน, media failure, AI backlog และพื้นที่เก็บ ใช้ backoff กับการขัดข้องชั่วคราว เมื่อเจอ challenge หรือ checkpoint ให้พัก source และแจ้งผู้ใช้ตรวจ session ด้วยตัวเอง กรณี disk ใกล้เต็มหยุดรับภาพใหม่และแจ้งเหตุ ผล scrape ที่ขาดภาพยังรายงานตามหลักฐานที่มี

## 8. เกณฑ์ราคา กราฟ และการเปิดใช้จริง

Trend MVP ใช้ค่ามัธยฐานราคาตั้งขายและ P25/P75 ของข้อเสนอที่เทียบกันได้ แสดง window และ n เทียบ SKU/VRAM, สภาพ, ชุด/ชิ้น, สกุลเงิน และหน่วย ใช้ราคาเสนอขายที่ยืนยันได้ครั้งแรกต่อข้อเสนอ จัดช่วงตามเวลาที่พบราคานั้นครั้งแรก เพื่อให้รายการที่กดติดตามถี่มีน้ำหนักเท่ากับรายการอื่น หลังรวม cross-post ที่ยืนยันได้แล้วให้แสดงข้อจำกัดกรณีที่ยังจับคู่ไม่ได้ ประวัติการปรับราคาของประกาศเดิมแสดงใน timeline ของประกาศ

ค่าเริ่มต้นเปรียบเทียบ 7 วันเต็มล่าสุดกับ 7 วันเต็มก่อนหน้า โดยตัดวันตาม Asia/Bangkok ใช้กลุ่มเดิมทั้งสองช่วง ต้องมีอย่างน้อย 10 ข้อเสนอและผู้ขายที่แยกได้อย่างน้อย 3 รายต่อช่วง เมื่อ coverage ของกลุ่มต่างกันอย่างมีสาระ เช่น กลุ่มหนึ่งถูกพักทั้งช่วง ให้แสดงค่าของแต่ละช่วงพร้อมข้อจำกัดและงดสรุปทิศทาง เมื่อผ่านเงื่อนไขคำนวณ Δ% = 100 × (median_now / median_prev − 1) ค่าเดิมต้องมากกว่าศูนย์ ขึ้นตั้งแต่ +5% ลงตั้งแต่ −5% ระหว่างนั้นแสดง “ใกล้เคียงช่วงก่อน” ป้ายนี้อธิบายข้อมูลย้อนหลัง แสดง n และ “ข้อมูลยังน้อย” เมื่อไม่ถึงเกณฑ์ ทั้งช่วงและเกณฑ์เป็นค่าตั้งต้นที่ปรับได้และต้องบันทึกพร้อมผล ห้ามนำราคาตั้งขายไปอ้างเป็นราคาที่ทำธุรกรรมสำเร็จ

Phase ถัดไปสร้าง graph เมื่อมีคำถามความสัมพันธ์ที่ต้องใช้จริง พร้อมชุดทดสอบเทียบ SQL, บันทึก projection lag และ replay/purge ผ่านก่อนเปิดอ่าน Graph ใช้ stable ID เดียวกับ SQL และ rebuild ได้ Forecast เริ่มได้เมื่อมีช่วงข้อมูลสำหรับทดสอบตามลำดับเวลา แยกชุดฝึกจากชุดอนาคต เปรียบเทียบค่าคลาดเคลื่อนกับ baseline เช่นมัธยฐานช่วงล่าสุด และประกาศเกณฑ์ผ่านก่อนประเมินจริง

ระยะ M ให้ทดสอบ AT-03, AT-05, AT-09 และ AT-11 ถึง AT-14 ตามฟีเจอร์ที่เปิดก่อนทดลองกับข้อมูลผู้ใช้จริง เก็บตัวอย่างจริงเฉพาะในขอบเขตที่ได้รับสิทธิ์ ประเมินเวลาตัดสินใจและการกลับมาใช้ซ้ำตาม [PRD](../product/PRD.md)

ลำดับเปิด Collector ในระยะ B คือ fixture acceptance → ตรวจสิทธิ์และ session isolation ของ adapter/เวอร์ชันที่ตรึง → ทดสอบ browser ด้วยข้อมูลที่มีสิทธิ์ในวงจำกัด → pilot 5 กลุ่มเมื่อครบเงื่อนไข ทดสอบกับ dummy credential ทั้ง Authorization, explicit cookie และ HTTP auth บน origin ที่สองทั้งการเปิดลิงก์และ redirect ต้องตรวจพบค่าหลุดออกไป 0 รายการ ข้อกำหนดนี้ครอบคลุมกรณีที่รายงานใน Scrapling #558 โดยไม่ถือว่ารายงานนั้นได้รับการพิสูจน์กับสแต็กนี้แล้ว วัดการแยกโพสต์ ผู้ขาย ภาพและสถานะเทียบกับการตรวจด้วยมือ บันทึกผลแยกต่อกลุ่ม หาก credentials รั่วข้าม origin หรือผูกผู้ขาย/ขายแล้วผิด ให้ปิด adapter จริงจนแก้และทดสอบ regression ผ่าน
