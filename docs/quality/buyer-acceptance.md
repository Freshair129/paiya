# ตรวจรับเส้นทางตั้งรับและเปรียบเทียบดีล

**สถานะ** แผนทดสอบและข้อมูลสังเคราะห์สำหรับทีมพัฒนา · 7 พฤศจิกายน 2026

QA ใช้กรณีนี้ตั้งแต่ schema และฐานข้อมูลถึง PWA เมื่อมีซอฟต์แวร์ที่รันได้ ให้บันทึก commit, migration, รุ่น adapter และรุ่นกฎ พร้อมผลจริงแยกตาม A (fixture), M (ผู้ใช้นำเข้า) และ B (แหล่งอัตโนมัติที่ได้รับอนุญาต) เป้าหมายคือกดจากดีลที่แจ้งเข้าถึงข้อความต้นทางของราคาและสถานะของสินค้าแต่ละชิ้นได้ [PRD](../product/PRD.md) · [SRS](../requirements/SRS.md) · [Traceability](TRACEABILITY.md)

## ชุดข้อมูลตั้งต้น

ใช้โพสต์จำลอง P มีสินค้า X = RTX 3060 12GB และ Y = RTX 3070 8GB โพสต์ Q มีสินค้า Z = RTX 3060 12GB วาง P และ Q คนละแหล่งจำลองโดยมี grant แยกกัน ทั้งสองแหล่งให้สิทธิ์อ่าน ทำสถิติ และเก็บข้อความที่ระบุไว้ สร้างกฎ R ในคลังว่างสำหรับ RTX 3060 12GB สภาพใช้งานได้ ราคาเสนอต่อชิ้นไม่เกิน 6,000 บาท ตัดรุ่น Ti ของเสียและยกชุดออก ผู้ทดสอบเปิดติดตามเฉพาะ X เมื่อมีสินค้าในคลัง ตัวระบุ P/Q/X/Y/Z/R เป็นชื่อย่อในรายงาน ผู้รันแมปไปยัง UUID ของรอบทดสอบ

| ขั้น | ป้อนข้อมูล/การกระทำ | สิ่งที่ตรวจจากฐานข้อมูลและหน้าจอ |
|---|---|---|
| 1 | วางลิงก์พร้อมข้อความของ P ที่ระบุรุ่น สภาพ ราคา X 6,300 และ Y 7,900 บาท ดูตัวอย่างแล้วกดยกเลิก จากนั้นเปิดตัวอย่างและยืนยัน | ตอนยกเลิก คลังและกล่องแจ้งเตือนเพิ่มศูนย์ รอบที่ยืนยันได้หนึ่งโพสต์ สองสินค้า ราคาสองชิ้นแยกกัน R ยังไม่แจ้ง ตรวจ log เครือข่ายแล้วไม่มีคำขอไปต้นทางระหว่างนำเข้า |
| 2 | ผู้ซื้อคอมเมนต์ “จองครับ” ป้อนหลักฐานที่ติดบทบาท seller ขัดกับเจ้าของคอมเมนต์ด้วย | ระบบปฏิเสธหลักฐานในฐานะคำยืนยันของผู้ขาย สถานะยืนยันเดิมคงอยู่ เก็บคำพูดเป็นกิจกรรมเมื่อสิทธิ์อนุญาต กรณีใหม่ต้องมี negative fixture สำหรับกฎตรวจบทบาทเดิม |
| 3 | ส่ง P รอบใหม่พร้อมคำยืนยันที่ระบุชิ้นชัดเจนว่า “3060 12GB ลดเหลือ 5,800 บาท ส่งใบนี้ 150” | ยังมีโพสต์ P เดิม ราคา ask ของ X = 5,800 ค่าส่งของ X = 150 พร้อมหลักฐาน R สร้างแจ้งเตือนหนึ่งรายการเมื่อข้ามงบ เปิดถึงคำยืนยันภายใน 3 ครั้งที่แตะจาก feed |
| 4 | ส่งคำขอเดิมพร้อมคีย์เดิมซ้ำ จำลอง worker หยุดหลังเขียนแล้วรันซ้ำ และป้อน observation เก่าภายหลัง | ไม่มีรอบหรือแจ้งเตือนซ้ำจาก retry รอบเก่าไม่ทับราคา 5,800 ทดสอบแยกด้วยการส่งครั้งใหม่ที่เนื้อหาเดิม รอบสังเกตใหม่เพิ่มได้แต่จำนวนเหตุการณ์เปลี่ยนราคาและแจ้งเตือนคงเดิม |
| 5 | ป้อนคำว่า “3070 ขายแล้ว” สองกรณีแยกกัน คือข้อความที่คัดลอกมาล้วน ๆ กับ fixture ที่ตรวจบทบาทผู้ขายได้จากหลักฐานแหล่งเดียวกับโพสต์ แล้วส่ง Q ระบุ Z ราคา 5,900 บาท สภาพใช้งานได้ แต่ไม่มีข้อความค่าขนส่ง | กรณีคัดลอกอย่างเดียวไม่มีการยืนยันขาย กรณี fixture ที่ยืนยันผู้พูดได้เปลี่ยนสถานะ Y พร้อมข้อความอ้างอิง ส่วน X คงสถานะเดิมและไม่มีแจ้งเตือน Watch ของ X จากการขาย Y กล่อง R มีแจ้งของ Z แยกเป็นคนละชิ้น |
| 6 | เลือก X และ Z มาเทียบ เปิดหลักฐานราคาของทั้งสอง และลองเพิ่มชิ้นที่สาม | แสดงยอดของ X = 5,950 บาท ยอดของ Z “ยังไม่ทราบยอดรวม” แสดง ask 5,900 พร้อมที่มา ข้อมูลค่าส่งที่หายยังเป็น unknown สภาพ/ประกันหรือสถานะที่ไม่มีหลักฐานแสดงว่ายังไม่ทราบ |
| 7 | เปลี่ยนสิทธิ์ของ P ระหว่างเปิดหน้าจอ ขอซ้ำผ่าน UI/API และ MCP ที่เคยมีสิทธิ์ จากนั้น purge และ restore สำเนาก่อนลบ | อ่าน X และหลักฐานเดิมไม่ได้ เรียกหน้าต่างเทียบ X+Z ซ้ำได้ 404 ทั้งคำขอ กล่องแจ้งเตือนซ่อน P และการขออ่าน Q แยกยังได้ตามสิทธิ์ หลัง restore ต้องบังคับการลบก่อนเปิดให้อ่านอีกครั้ง |

ก่อนทดสอบให้บันทึกจำนวนแถวตามโพสต์ สินค้า เหตุการณ์ และชนิดการแจ้งเตือน การตั้งรับกับการติดตาม X เป็นคนละการสมัคร จึงตรวจจำนวนแยกตามกฎ R หรือ Watch ของ X [สัญญาฝั่งผู้ซื้อ](../architecture/contracts/buyer-workflows.md) · [แบบจำลองข้อมูล](../architecture/data-model.md)

## กรณีขอบเพิ่มเติม

- สร้าง R เมื่อ X อยู่ในงบแล้ว ผลค้นเห็น X ได้ทันทีและจำนวนแจ้งย้อนหลังเป็นศูนย์ เปลี่ยนราคาจาก 5,800 → ยังไม่ทราบ → 5,800 ต้องไม่แจ้งซ้ำ ถ้าราคาออกนอกงบเป็น 6,100 อย่างยืนยันได้แล้วลดเหลือ 5,950 จึงแจ้งรอบใหม่หนึ่งครั้ง
- ข้อความ “มัดจำ 500” หรือ “RTX 3060 Ti” ต้องไม่สร้างแจ้งตรงกฎ R สำหรับ 3060 12GB ทดสอบคำว่า “รวมส่ง” เทียบกับไม่ระบุค่าส่ง และค่าส่งรวมทั้งโพสต์หลายชิ้นที่แบ่งรายชิ้นไม่ได้
- ส่งคีย์เดิมกับข้อความคนละเนื้อหา ปฏิเสธคำขอและรักษารอบเดิม ลิงก์ย่อที่ต้องออกไปแกะปลายทางให้แสดงวิธีนำ permalink มาใส่แทนตามสัญญา
- ที่ viewport 360 CSS px ทดสอบการยืนยัน นำทางด้วยคีย์บอร์ด อ่านราคา/เวลา/หลักฐานและเปรียบเทียบ 2–3 ชิ้นโดยหน้าไม่เลื่อนแนวนอน มือถือจริงต้องใช้ HTTPS กับ session ที่ยืนยันตัวตนแล้ว

## ทดลองกับผู้ซื้อ

| รอบ | วิธีเก็บผล | ตัวหารและเกณฑ์ตัดสิน |
|---|---|---|
| M · เลือกดีล | ให้ผู้ซื้อเทียบประกาศสองรายการแล้วเปิดข้อความรองรับราคา ทำทั้งวิธีที่ใช้อยู่กับป้ายยา สลับลำดับหรือชุดโจทย์ที่มีความยากใกล้กัน บันทึกเวลาและงานที่ทำไม่จบ | รายงานจำนวนคู่ที่ทำจบ เวลามัธยฐานในแต่ละวิธี และผลต่างรายคน รายงานคนที่ติดขั้นนำเข้ารวมถึงเหตุผลแยกไว้ |
| M · กลับมาใช้อีก | หลังครั้งแรกให้ใช้งานตามปกติ นับคนที่กลับมาเพิ่มข้อเสนอคนละรายการด้วยตนเองภายในเจ็ดวัน | ตัวเศษคือผู้ที่เพิ่มดีลที่สอง ตัวหารคือผู้เข้าทดลองที่เริ่มใช้งานครั้งแรกและติดตามครบเจ็ดวัน ระบุจำนวนที่ยังติดตามไม่ครบ Product owner กำหนดเกณฑ์ตัดสินก่อนเริ่ม pilot และบันทึกผลก่อนลงทุนกับ OCR |
| B · พบประกาศใหม่ | เทียบโพสต์ที่ Collector พบกับโพสต์เข้าเกณฑ์ที่ผู้ทดสอบเห็นในรอบ กลุ่ม ลำดับและขอบเขตการเลื่อนเดียวกัน | ระบุจำนวนที่พบ/จำนวนที่ผู้ทดสอบเห็น แยกกลุ่มและรอบที่ข้อมูลไม่ครบ ใช้เกณฑ์หยุดและขยาย B ตาม SRS และ Roadmap |

แนบต่อรอบเฉพาะ fixture สังเคราะห์หรือสถิติที่เผยแพร่ได้ ผล AT และผลผู้ใช้ต้องลงใน [ตารางติดตาม](TRACEABILITY.md) หลังทดสอบบน commit ที่ระบุ
